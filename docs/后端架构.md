# 后端架构文档

> 目的：让每次开启新对话的 AI（或新接手的开发者）读完这一篇，就能快速上手本项目。
> 项目进度截至阶段 **4.1（双 Agent 流水线）**，更后续阶段见文末「后续路线」。

---

## 1. 项目定位与技术栈

**AI 智能面试官**：基于 Spring AI Alibaba 1.1 从 0 到 1 构建的多 Agent 面试陪练系统，具备记忆、知识检索（题库 RAG）、工具调用三大核心能力。一句话：**「用自己做的 AI 面试官准备面试」**。

| 层 | 选型 | 版本 |
|---|---|---|
| 框架 | Spring Boot | 3.5.7 |
| AI | Spring AI | 1.1.2 |
| AI | Spring AI Alibaba | 1.1.2.0 |
| 模型接入 | 阿里百炼 OpenAI 兼容协议 | qwen3.7-plus / qwen3.7-text-embedding |
| 短期记忆 / 向量检索 | Redis Stack | latest |
| 业务数据持久化 | PostgreSQL | 16 |
| 数据访问 | Spring Data JPA | - |
| Web | WebFlux（Netty，SSE 流式） | - |
| 容器 | Docker Compose | - |

> ⚠️ DashScope 原生协议在本项目不可用，必须走 OpenAI 兼容端点 `https://dashscope.aliyuncs.com/compatible-mode`。

```
                      ▼

              ┌────────────────┴────────────────┐
              ▼                                 ▼

  (SequentialAgent，4.1)               (ReactAgent：出题/追问/评估)

   ▼              ▼

   │ saveCodeProfile 落库    getCodeFacts / loadCodeFacts 取库
   ▼              ▼
      code_profile 表（数据契约载体：落库传递，重开会话复用）
                       ▼
                  Agent 核心能力层
   ┌──────────────┬──────────────┬──────────────────┐
   ▼              ▼              ▼                  ▼
短期记忆        工具调用        知识检索          MCP 工具生态
Redis 滑动窗口  @Tool 自定义    RedisStack 向量库   Filesystem(只读)
(会话隔离)     (评分/统计/清单) (题库+Embedding)   (读候选人代码)
   │              │              │                  │
   └──────────────┴──────────────┴──────────────────┘
                              ▼
                   Redis Stack │ PostgreSQL (业务数据+题库元数据)
```

> 当前已落地：短期记忆 + 知识检索（RAG）+ ReactAgent 显式推理（阶段 3）+ Function Calling 工具 +
> MCP Client（Filesystem）+ 双 Agent 流水线（4.1：代码分析 Agent → 面试官 Agent，SequentialAgent 编排）。
> MCP 方向调整：不做自研 MCP Server（题库/评分工具强绑定内部会话，无外部复用价值），
> 改为作为 MCP Client 接入官方 Filesystem Server，读取候选人本地代码做代码评审式面试，
> 突破静态 RAG 题库的知识局限。ReadOnlyMcpToolFilter 过滤写操作，保证只读安全。
> 记忆演进：阶段 3 起砍掉"会话内摘要式长期记忆"（qwen 1M 上下文窗口远够用，论证见项目计划书），
> 跨会话薄弱点回顾推迟到 4.3（走 SQL 聚合 score_record，不走摘要/向量化）。

### controller

**AssistantController** —— `/api/assistant`
- `POST /chat`（`text/event-stream`）：请求体 `{userMessage, sessionId}`，返回 `Flux<String>` 流式面试回答。
- 历史版本是 GET + query 参数，因面试回答过长会撞 URL 长度上限，已改为 POST + SSE。

**MemoryController** —— `/api/assistant/memory`
- `GET /` ：列出所有会话 id（能力在 `ChatMemoryRepository`，`ChatMemory` 接口无此方法）
- `GET /{sessionId}` ：该会话滑动窗口内消息（最多 20 条），返回 `ChatMessageDto{role,content}`
- `DELETE /{sessionId}` ：清空会话记忆，返回 `ClearResult{sessionId,cleared}`

**KnowledgeBaseController** —— `/api/knowledge`
- `POST /sync` ：手动触发同步（外部目录 + classpath 兜底），返回 `{message,totalDocuments}`
- `GET /documents` ：文档元数据列表 `[{fileName,chunkCount,status,source,ingestedAt}]`

### services

**CodeAnalyzerAgent** —— 代码分析 Agent（分析型，4.1 新增）
- ReactAgent + MCP Filesystem 工具（read_file/list_directory 等）+ 内置工具 `saveCodeProfile`
- `analyze(userMessage, sessionId)`：**同步** `agent.invoke()`——读代码 → LLM 产出结构化 JSON 事实清单 → 调工具落库
- `getAgent()`：把内部 ReactAgent 透出给编排器（SequentialAgent 要求子 Agent 是 Agent 类型）
- 一次性任务：无记忆、无 checkpoint（builder 不配 saver）
- prompt 核心是"输出什么结构"：JSON schema 示例 + 三字段约束（techStack/designPatterns/implementationDetails/riskPoints/followUpPoints），与对话型 prompt 相反

**CodeReviewPipeline** —— 双 Agent 流水线（4.1 新增）
- 构造：`SequentialAgent.builder().subAgents(分析官, 面试官)`，列表顺序 = 执行顺序（先分析、后面试）
- `codeReviewChat(userMessage, sessionId)` 两条路径：
  - 复用路径：`codeProfileRepository.existsBySessionId` 命中 → 跳过分析官，直接面试官 `chat()`（落库复用的红利，省一次分析）
  - 流水线路径：首次 → `pipeline.streamMessages()` 完整链路（分析官落库 → 面试官 getCodeFacts 取库出题）
- `isCodeReviewRequest(userMessage)`：规则版意图判断（盘符路径/文件扩展名/关键词），4.2 升级 LlmRoutingAgent
- 编排管时序、数据走数据库：SequentialAgent 只保证顺序，不负责传数据（"接力棒"通过 code_profile 传递）

**InterviewAssistant** —— 面试官 Agent（对话型，阶段 3.1 ReactAgent 重构 + 4.1 改造）
- ReactAgent（替代 ChatClient）：「思考→行动→观察」显式推理循环，MemorySaver 按 threadId=sessionId 隔离 checkpoint，单次运行结束 release
- 无 Advisor：RAG 检索、短期记忆读写、事实清单注入全是手动组装消息（`chat()` 第 1 步）
- `chat(userMessage, sessionId)`：组装消息（loadCodeFacts 清单 → searchKnowledge 题库 → 窗口历史 → 用户消息）→ `streamMessages` 流式 → 收尾写回窗口 + release
- `loadCodeFacts(sessionId)`：从 code_profile 表取事实清单 JSON 原文注入 system 消息（4.1 数据契约消费端）
  - **直接传原文、不做 Jackson 解析**：清单唯一读者是 LLM 且 LLM 读 JSON 是强项；只有"代码要程序化处理"才解析（判据：LLM 消费传原文、代码消费才解析）
- `getAgent()`：透出 ReactAgent 给编排器
- `sessionId` 不进模型可见参数：从 `RunnableConfig.threadId` 注入，工具经 `ToolContext` 取回，会话隔离最稳

**KnowledgeBaseService** —— 知识库同步
- `syncKnowledgeBase(resourceLocation, source)`：扫描 `*.txt` → 逐文件 `ingestFile` → `removeDeletedFiles` 增量删除
- `ingestFile`：读内容 → MD5 哈希 → 查 PG 元数据 → 哈希相同跳过（幂等）→ 变更/新增则 `TokenTextSplitter` 分块 → 带 `docId/chunkIndex` 元数据写入 Redis 向量库 → 更新 PG 元数据
- `deleteVectorChunks(docId, chunkCount)`：按 `docId_i` 拼 ID 删除向量块
- 分块器：`TokenTextSplitter` 默认 cl100k_base，约 800 token/块

### config

**AgentConfig**
- `chatMemoryRepository`：`JedisRedisChatMemoryRepository`（memory-redis starter 无自动装配，手动建 Bean，连接参数复用 `spring.data.redis.*`）
- `chatMemory`：`MessageWindowChatMemory`，maxMessages=60 滑动窗口（阶段 3 起不被 Advisor 自动注入，改由 InterviewAssistant 手动读写窗口）
- `memorySaver`：`MemorySaver` 内存版 checkpoint 保存器（RedisSaver 依赖 Redisson 客户端、与向量库强依赖的 Jedis 冲突，不用；单次运行结束即 release，不会无限累积）
- 阶段 3 起不再配置 `MessageChatMemoryAdvisor` / `QuestionAnswerAdvisor`：ReactAgent 不走 ChatClient  advisor，RAG 检索 / 记忆 / 清单注入全部由各 Agent 在 chat() 里手动做

**KnowledgeBaseLoader** —— `ApplicationRunner`，启动时自动加载
- 解析 `app.knowledge.path`（`file:./data/knowledges/`）
- 目录不存在 → 创建 + 回退 classpath；为空 → 回退 classpath；有文件 → 用外部题库
- 加载失败不影响应用启动（仅失去 RAG 能力）

**HttpClientConfig**
- `RestClient.Builder` 用 `JdkClientHttpRequestFactory`（非流式），`WebClient.Builder` 用 `JdkClientHttpConnector`（SSE 流式）
- 两者都改 JDK 客户端，彻底避开 Netty 异步 DNS 在某些网络环境超时（流式此前单独撞过此问题）

### tools

**InterviewTools** —— 面试官工具集（@Tool + @ToolParam 注解注册，`sessionId` 从 `ToolContext` 取）
- `scoreRecord(topic, question, answer, score, feedback, ToolContext)`：单题评分落库；分数钳制 0~10；同会话同题幂等（更新不新增）
- `questionStats(ToolContext)`：按考点聚合答题数/平均分/最低分，标注平均分<6 的薄弱考点
- `calculator(values, op)`：纯函数计算（average/sum/percentage），避免模型算术幻觉
- `getCodeFacts(ToolContext)`（4.1 新增）：面试官**主动拉取**事实清单——在 SequentialAgent 流水线里面试官作为子 Agent 跑，外层无法在其开始前前置注入，只能靠 LLM 自己调工具取库（与 loadCodeFacts 前置注入互补：注入在重开场景、拉取在流水线场景）

**CodeAnalyzerTools** —— 分析官工具集（4.1 新增）
- `saveCodeProfile(filePath, factsJson, ToolContext)`：事实清单落库 code_profile，sessionId 从 ToolContext 取
- 为什么落库用 @Tool 让 LLM 自己触发：SequentialAgent 自动按序执行子 Agent，外层代码没有"分析完、面试开始前"的中间钩子可插，所以由 LLM 分析完主动调工具落库（与 scoreRecord 同模式）

### entity / repository

**CodeProfile**（PG 表 `code_profile`，4.1 新增）
- `id`(PK, 自增) / `sessionId` / `filePath` / `factsJson`(text) / `createdAt`
- `factsJson` 存整段 JSON（techStack/designPatterns/implementationDetails/riskPoints/followUpPoints）：
  AI 产出是半结构化（风险点数量可变），"宽表存 JSON、应用层解析"，不拆固定列
- 数据契约物理载体：分析官写、面试官读，落库传递支持"重开会话不重复分析"

**CodeProfileRepository**
- `findBySessionIdOrderByCreatedAtAsc`：按会话取全部清单（一个会话可能分析多个文件，合并出题）
- `existsBySessionId`：判断"该会话分析过没"——复用路径开关，决定是否跳过分析官

**KnowledgeDocument**（PG 表 `knowledge_document`）
- `id`(PK, 自增) / `fileName`(唯一) / `chunkCount` / `contentHash`(MD5, 64) / `status`(枚举) / `source`(EXTERNAL/CLASSPATH) / `ingestedAt`
- 幂等比对靠 `contentHash` + `fileName`

**KnowledgeDocStatus**：`INGESTED` / `FAILED`

**KnowledgeDocumentRepository**：`findByFileName` / `existsByFileName` + JPA 基础方法

**ScoreRecord**（PG 表 `score_record`）
- `id`(PK, 自增) / `sessionId` / `topic`(考点) / `question` / `answer` / `score`(0~10) / `feedback` / `createdAt`
- `createdAt` 由服务端落库时生成，不依赖 LLM 传时间
- 题目文本直接冗余存储，不建外键关联题库文档（题库文档会被增量清理，外键反而埋隐患）

**ScoreRecordRepository**
- `findBySessionIdOrderByCreatedAtAsc` / `findBySessionIdAndQuestion`（幂等去重）/ `aggregateByTopic`（GROUP BY 考点聚合）

## 4. API 契约表

| 方法 | 路径 | 入参 | 返回 | 说明 |
|---|---|---|---|---|
| POST | `/api/assistant/chat` | body `{userMessage, sessionId}` | `text/event-stream`（`Flux<String>`） | 面试对话，SSE 流式 |
| GET | `/api/assistant/memory` | - | `string[]` | 所有会话 id |
| GET | `/api/assistant/memory/{sessionId}` | path | `[{role,content}]` | 会话历史（滑动窗口内） |
| DELETE | `/api/assistant/memory/{sessionId}` | path | `{sessionId,cleared}` | 清空会话 |
| POST | `/api/knowledge/sync` | - | `{message,totalDocuments}` | 手动同步知识库 |
| GET | `/api/knowledge/documents` | - | `[{fileName,chunkCount,status,source,ingestedAt}]` | 文档元数据列表 |

> 默认 `sessionId=default`。SSE 数据为纯文本分片（`Flux<String>`），前端按 text/event-stream 增量拼接。
> ⚠️ Spring 的 SSE 写出器会自动把分片内 `\n` 转成 `\ndata:` 续行（**控制器切勿再手动转义**，否则双重转义会在页面混入多余的 `data:` 文字）；前端 `sse.ts` 把同帧多条 `data:` 行按 `\n` 拼接还原换行，否则换行全丢、回答挤成一段。

## 5. 数据存储说明

### Redis Stack（6379，可视化 8001）
- **短期记忆**：`JedisRedisChatMemoryRepository`，key 按 `sessionId`（即 `chat_memory_conversation_id`）隔离
- **向量索引**：`ai-agent-index`，prefix `ai-agent-doc`，1024 维（qwen3.7-text-embedding 默认）
- 块 ID = `文件名_i`，元数据含 `docId`/`chunkIndex`

### PostgreSQL（5432，admin/admin123，库 aiagent）
- 表 `knowledge_document`（JPA `ddl-auto=update` 自动建/改）：题库文档元数据
- 表 `score_record`：单题评分记录（阶段 2.3），字段见上「ScoreRecord」
- 表 `code_profile`：代码分析事实清单（阶段 4.1），字段见上「CodeProfile」

## 8. 关键风险 / 注意点

1. **Redis 必须 Stack 版**（普通 Redis 无 RediSearch 向量模块，报 `unknown command 'FT._LIST'`）
2. **向量库强依赖 Jedis**：`spring.data.redis.client-type=jedis` + `commons-pool2`，否则 `VectorStore` Bean 创建失败
3. **Windows 中文 JVM 默认 GBK** → 中文乱码：`.mvn/jvm.config` 已加 `-Dfile.encoding=UTF-8`（作用于 Maven 本体）→ **fork 出的应用进程不继承它**，必须再在 `spring-boot-maven-plugin` 配 `<jvmArguments>-Dfile.encoding=UTF-8</jvmArguments>`（4.1 验收实测踩坑）；IDEA 运行配置 VM options 也要加
4. **向量维度对齐**：qwen3.7-text-embedding 默认 1024 维，与索引一致；换模型/改 dimensions 需先查索引维度
5. **6379 抢占**：本机若有原生 Redis 会抢占端口且无向量模块，需 `net stop Redis`
6. `initialize-schema: true` 首次启动建索引，之后可改 false
7. API Key 开发期硬编码，公开仓库前移到环境变量并去百炼控制台重置（旧 key 已在 git 历史里）
8. PG 连接信息以根目录 `docker-compose.yml` 为准（admin/admin123，库 aiagent）
9. 外部知识目录 `data/knowledges/` 默认 gitignore，示例题库放 `resources/knowledges/` 兜底
10. 每个阶段结束 git commit，方便简历展示 commit 历史
11. **SSE 流式走 WebClient**：若流式接口报错，先排查 DNS——`RestClient`（非流式）和 `WebClient`（流式）要分别覆盖，`HttpClientConfig` 两者都改 JDK 客户端已规避
12. **Function Calling 需验证 SSE 流式下的工具触发**：Spring AI 流式默认会执行工具调用并回填，但工具触发的中间 token 会混进流，前端按 SSE 拼接时无需特殊处理
13. **模型重复调用工具**：同一道题可能被多次落库，`scoreRecord` 已按 `sessionId+question` 幂等去重
14. **MCP 管道编码坑（兼容 3，4.1 验收实测）**：应用 JVM 若不是 UTF-8，`read_file` 返回的中文注释会被 GBK 误解码，乱码中恰好吞掉 JSON 引号 → `JsonParseException` → MCP 通道瘫痪、后续工具全部 60s 超时。症状像"MCP 超时"，根因是编码，先查 JVM `file.encoding` 再怀疑 MCP 本身
15. **SequentialAgent 流式会混入分析官输出（计划书风险 14 实测确认）**：`pipeline.streamMessages()` 会把分析 Agent 的思考文字也流给前端（用户会先看到"让我再读取……"的分析过程再看到题目）。不影响功能，4.2 做路由时可优化过滤

```bash
# 1. 中间件
docker compose up -d
```
