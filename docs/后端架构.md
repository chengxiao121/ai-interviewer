## 1. 项目定位与技术栈

**AI 智能面试官（能力评估系统）**：基于 Spring AI Alibaba 1.1 从 0 到 1 构建的多 Agent 评估系统——输入 JD/简历/代码，多 Agent 并行画像，按《面试计划》实时自适应考核，输出**带证据链的《面试评估报告》**。具备记忆、知识检索（题库 RAG）、工具调用、评估闭环四大核心能力。

> 产品立场（阶段 5 重定义）：不是聊天陪练，是**可验证的能力评估**。"报告可信"在结构上要求五件事，
> 每件对应一个组件（拿掉任何一个报告就不成立）：范围契约（interview_plan 计划）、考官与评分分离
> （AnswerEvaluatorService）、考点词表封闭（计划词表 = 评分归类与覆盖 join 的唯一基准）、
> 证据可溯（score_record 逐题留痕 + 报告证据链）、跨场次采样（candidateId 聚合）。
> 另一条全局判据：**LLM 调用 ≠ Agent**——只有需要工具循环/临场决策的环节才配 ReactAgent
> （面试官 + 三个分析官，共 4 个），规划/评估/报告都是"带 LLM 的普通函数"。

| 层 | 选型 | 版本 |
|---|---|---|
| 框架 | Spring Boot | 3.5.7 |
| AI | Spring AI | 1.1.2 |
| AI | Spring AI Alibaba | 1.1.2.0 |

| 短期记忆 / 向量检索 | Redis Stack | latest |

> 当前已落地：短期记忆 + 知识检索（RAG）+ ReactAgent 显式推理（阶段 3）+ Function Calling 工具 +
> MCP Client（Filesystem）+ 双 Agent 流水线（4.1）+ 意图路由 LlmRoutingAgent + 并行分析 ParallelAgent（4.2）
> + 反馈闭环：跨会话薄弱点回顾（4.3）
> + **评估系统（5.1~5.5）：面试计划（范围契约）/ 会话内评估闭环（评分落库代码侧，修风险 23）/
>   带证据链的评估报告（独立端点）/ 流水线收敛（两套并一套，路由规则前置两路）**。
> 5.x 核心判据：LLM 调用 ≠ Agent——真 ReactAgent 保持 4 个（面试官 + 分析官×3）不变，
> 规划/评估/报告是 service 方法 + 一次结构化 LLM 调用。
> 4.2 裁剪决策：不设独立闲聊 Agent（面试官吸收寒暄，避免第三路误路由，理由同"不单独做知识 Agent"）。
> MCP 方向调整：不做自研 MCP Server，改为 MCP Client 接入官方 Filesystem Server（ReadOnlyMcpToolFilter 只读安全）。
> 记忆演进：阶段 3 起砍掉"会话内摘要式长期记忆"（qwen 1M 上下文窗口远够用，论证见计划书）；
> 4.3 已落地"跨会话薄弱点回顾"：候选人维度 SQL 聚合 score_record → 开场注入 / 工具主动取，
> 走 SQL 聚合（精度高、零幻觉），不走摘要/向量化。

### controller

**AssistantController** —— `/api/assistant`
- `POST /chat`（`text/event-stream`）：请求体 `{userMessage, sessionId}`，返回 `Flux<String>` 流式面试回答。
- 历史版本是 GET + query 参数，因面试回答过长会撞 URL 长度上限，已改为 POST + SSE。

**AssessmentController** —— `/api/assessment`（5.4 新增）
- `GET /{sessionId}/report?candidateId=`：生成并返回《面试评估报告》结构化 JSON（同步非流式，无副作用可重复调用）。
- 报告是交付物不是对话流：独立端点、不进意图路由——寒暄永远不会被误分到"生成报告"；接口层面区分"对话流（SSE）"与"判定结果（JSON）"。

**MemoryController** —— `/api/assistant/memory`
- `GET /` ：列出所有会话 id（能力在 `ChatMemoryRepository`，`ChatMemory` 接口无此方法）
- `GET /{sessionId}` ：该会话滑动窗口内消息（最多 20 条），返回 `ChatMessageDto{role,content}`
- `DELETE /{sessionId}` ：清空会话记忆，返回 `ClearResult{sessionId,cleared}`

**KnowledgeBaseController** —— `/api/knowledge`
- `POST /sync` ：手动触发同步（外部目录 + classpath 兜底），返回 `{message,totalDocuments}`
- `GET /documents` ：文档元数据列表 `[{fileName,chunkCount,status,source,ingestedAt}]`

### services

**AgentRouter** —— 意图路由 Agent（4.2 新增，5.5 改版：规则前置 + 两路语义路由，统一入口）
- 三道关口（能过前两道的不花路由 LLM 调用——"能确定答案的便宜事，不必每次都问 LLM"）：
  - ① 复用快路径：`existsBySessionId && detectMaterials 为空`（已分析过 + 无新资料）→ 直连面试官 `chat()`
  - ② 规则路径：`detectMaterials` 命中资料（路径/扩展名/关键词）→ 直接进 MaterialInterviewPipeline（组合判断确定性 100%，省路由 LLM）
  - ③ 语义路由：`LlmRoutingAgent` 两路 `subAgents(materialInterviewPipeline.getPipeline(), interviewer.getAgent())`，fallback=interviewer——只兜规则漏掉的语义表述（"帮我看看上周写的那个线程池"）
- 路由机制（读框架源码）：路由节点把子 Agent 的 name+description 列给路由 LLM，LLM 返回 Agent 名列表（可一个或多个），校验失败自动重试，最终失败走 fallbackAgent；`ROUTING_INSTRUCTION` 写"拿不准 → interviewer"，与 fallbackAgent 双保险
- 语义路径的通用上下文只组装一次（薄弱点注入 → 面试计划(5.2) → RAG → 窗口历史 → 用户消息，路由发生在图内部，无法先路由再定制）→ config `.addMetadata(SessionKeys.CANDIDATE_ID_KEY, candidateId)`（4.3 metadata 写端）→ 过滤 AssistantMessage → 收尾写回窗口 + release
- 5.5 为什么从三路并两路：旧 code-review / combined 两条流水线是同一模式的两份拷贝，收敛后"挂哪几个分析官"由资料规则决定，路由 LLM 只需回答"是不是带资料的分析型面试"——判断维度越少，概率路由越准
- 裁剪决策（延续）：不设独立闲聊 Agent（面试官 prompt 吸收寒暄引导回面试），避免误路由上下文断裂

**ProfileAnalyzerAgent** —— 分析型 Agent 基类（4.2 重构，Rule of Three；5.5 加资料守门）
- 触发点：代码/JD/简历三个分析官同构三次，抽共同骨架（ReactAgent 拼装 / MCP 注入 / outputKey(name) / getAgent / analyze 同步执行）
- 子类只提供：name / description / systemPrompt（三样私有物）；注意用构造参数传 prompt 而非抽象方法（避免父类构造器调子类未初始化字段的坑）
- `outputKey(name)`：ParallelAgent 合并的要求——每个子 Agent outputKey 必须唯一（实测：不设警告、设相同值校验拒绝 Duplicate output keys）
- **【资料守门】（5.5）**：基类统一把守门条款拼进每个分析官 systemPrompt——上下文没有自己负责的资料时直接结束、禁止调工具、禁止落库、禁止编造。背景：路由注册的是全量分析官组合，"缺哪类资料"由分析官运行时自筛；也兜住规则误报（关键词命中但资料不在场），把"没资料"变成显式且极简的执行路径

**CodeAnalyzerAgent / JdAnalyzerAgent / ResumeAnalyzerAgent** —— 三个分析官（4.1 + 4.2）
- 同构模式：读资料（MCP read_text_file）→ LLM 产出结构化事实清单 → `saveCodeProfile(type=CODE/JD/RESUME)` 落库
- prompt 核心差异 = 输出结构：代码产 techStack/riskPoints/followUpPoints；JD 产 roleOverview/interviewFocus；简历产 skillProfile/weaknessCandidates（"疑似薄弱需验证"而非断言）
- 输入双通道：本地文件（MCP 读）或对话粘贴文本；prompt 硬性要求"只用 read_text_file、只读自己的文件、最后一步必须落库"（实测 LLM 会漂移：不强化时曾跑去 directory_tree 且不落库）

**MaterialInterviewPipeline** —— 资料分析流水线（5.5 新增，收敛 4.1 代码评审 + 4.2 综合面试两套同构类）
- 结构两层嵌套：`SequentialAgent( ParallelAgent(选中的分析官×N), interviewer )`——内层并行（各资料分析彼此独立），外层串行（面试必须等分析完拿到物料）
- 按组合缓存构建：`pipelineCache` 以资料 bitmask（CODE=1/JD=2/RESUME=4）为键，最多 8 种组合，`computeIfAbsent` 保证同组合只 build 一次（延续"build 一次复用"模式）
- `detectMaterials(userMessage)`（静态，AgentRouter 共用）：规则检测消息提到的资料——code=盘符/扩展名/评审关键词（自旧 isCodeReviewRequest 迁移），JD=岗位/JD/职位，简历=简历/resume/CV；三类独立检测、可叠加
- `chat(userMessage, sessionId, candidateId)` 两条路径：
  - 复用路径（按类生效，泛化自 4.1 的整体判断）：本轮提到的资料全部已有对应 profileType 清单（或没提资料、被语义路由带进来）→ 直连面试官 `chat()`，一次分析官调用都不花
  - 流水线路径：只对缺的类型跑分析官 → 面试官出题；`buildChatMessages` 组装上下文（含计划注入 5.2）
- `getPipeline()`：透出【全量组合】图给 AgentRouter 注册为路由子 Agent——路由 LLM 只判断"是不是资料面试"，具体挂哪几个分析官由分析官【资料守门】运行时自筛
- 编排管时序、数据走数据库：接力棒（事实清单）通过 code_profile 传递（4.1 契约延续）；分析官输出文字混进流属预期（风险 15）

**InterviewPlanService** —— 面试规划（5.2 新增，"带 LLM 的普通函数"，非 Agent）
- `ensurePlan(userMessage, sessionId, candidateId)`：保证该会话存在《面试计划》（幂等，一场一份）——查库命中直接返回；无则生成落库（有 JD 画像以 JD 考察矩阵为主依据 source=JD，否则按用户消息出临时计划 source=USER）
- USER→JD 自动升级：后续轮次发现"计划是 USER 版 + 该会话已落 JD 画像"（`existsBySessionIdAndProfileType`）→ 用 JD 画像重生成一次。覆盖矩阵以最终 JD 计划为基准，临时计划期题目不在最终词表内的按"计划外"如实呈现
- 三个消费方：面试官（`renderPlan` 渲染【面试计划】system 注入，每轮注入文本小成本可忽略）/ 评估官（`parseTopics` 取封闭考点词表）/ 报告（覆盖矩阵对照基准）
- 失败降级：解析失败重试 1 次（`LlmJson` 清洗 + Jackson 解析 + 词表清洗去重归一），仍失败返回 null → 调用方跳过注入，面试不阻塞（计划是增强项不是阻塞项）
- 落库由本服务代码直接执行（不经 LLM 工具），写 interview_plan 表

**AnswerEvaluatorService** —— 答案评估（5.3 新增，"带 LLM 的普通函数"，非 Agent）
- `evaluateTurn(userMessage, sessionId, candidateId, plan)`：InterviewAssistant.chat() 每轮第 0 步**确定性调用**（不靠模型自觉），在出题之前——评估结论要影响本题难度方向
- 自门控：结构化输出 `{isAnswer, topic, question, score, strengths, gaps, nextSuggestion}`——寒暄/反问/请求换题 → isAnswer=false → 不落库不注入（代替脆弱的正则启发式）
- **评分落库由代码直接执行**（幂等沿用 sessionId+question 去重、分数钳制 0~10、列长截断防御）——scoreRecord 工具已删除，score_record 唯一写入方收口到这里，**结构性修掉风险 23**（flash"用嘴打分不落库"）
- 考点词表封闭：topic 三级校验（精确 → 包含归一到词表措辞 → 兜底"计划外：<原文>"）；词表为空（无计划）退化为自由归类（4.3 行为）
- 返回 injectionText（【上一题评估】system 文本）注入面试官 → 下一题**当场**调难度/方向——反馈周期从"跨会话"缩到"跨单题"
- 失败降级：解析失败重试 1 次，仍失败本轮不评分不注入（WARN），面试继续

**AssessmentReportService** —— 评估报告（5.4 新增，"带 LLM 的普通函数"，非 Agent）
- `generate(sessionId, candidateId)` → 报告 JSON（LinkedHashMap 保序）：plan / coverage（逐考点：planned、题数、均分、最低分、证据链[题目/回答节选/得分/点评]）/ uncoveredTopics（计划有实际无）/ outOfPlanTopics（实际有计划无）/ crossSessionWeakness（WeaknessProfileService 文本）/ conclusion（overallSummary/matchConclusion/recommendations）
- 核心分工（反幻觉护栏）：**数字由 Java 算**（score_record 内存分组聚合 + 计划词表精确/包含双级匹配，可对账可复现），**叙事由 LLM 写**（一次调用，prompt 明令只许解读给定数字、禁止自造）
- 挂在独立端点 GET /api/assessment/{sessionId}/report 后面（AssessmentController），不进聊天路由
- 降级：无计划会话可出报告（仅实际统计，注明无计划基准）；结论生成失败（重试 1 次后）写占位文本，报告结构不缺角

**LlmJson** —— LLM 结构化输出清洗（5.2 新增，包私有工具类）
- 规划/评估/报告的输出都要被代码程序化处理（判据：LLM 消费传原文、代码消费才解析），解析前统一走 `extract()`：剥 ``` 围栏 + 截取首个 {/[ 到最后一个 }/]（掐掉前后解释文字）
- 提取不到结构时原样返回，让上层 Jackson 报错走重试/降级（不在这里吞异常）

**KnowledgeSearchService** —— 题库知识检索（4.2 重构）
- Rule of Three 触发点：`searchKnowledge` 在四个类复制（InterviewAssistant/CodeReviewPipeline/AgentRouter/CombinedInterviewPipeline），抽成唯一真源
- `search(String query)`：similaritySearch(topK=3, 门槛 0.7) → 拼成【题库知识】system 文本，无命中返回空串

**WeaknessProfileService** —— 跨会话薄弱点回顾（4.3 新增）
- 唯一数据源：`loadProfile(candidateId)` = 候选人维度 SQL 聚合（`aggregateByTopicForCandidate`，答题数/平均分/最低分，标注 avg<6 薄弱考点）→ 摘要文本
- 两个消费方共用同一段文本：`getWeaknessProfile` 工具（模型主动调）与开场注入（system 消息），口径不漂移；与 KnowledgeSearchService 同类"物料装配"模式
- 无评分记录返回空串 → 调用方跳过注入（新候选人开场干净，不虚构历史）

**StreamingPipelineSupport** —— 流式流水线基类（4.2 重构 + 4.3/5.2 扩展）
- 编排模板重复（组装上下文 → 跑图 → 过滤收尾）抽成基类：AgentRouter / MaterialInterviewPipeline 继承
- `buildChatMessages(userMessage, sessionId, candidateId)`（4.3 加 candidateId）：①薄弱点注入（WeaknessProfileService.loadProfile，有历史才注入）→ ①b 【面试计划】注入（5.2，ensurePlan 幂等，生成失败跳过）→ ②题库知识 → ③窗口历史 → ④用户消息；一处改动，所有流水线路同时生效

**InterviewAssistant** —— 面试官 Agent（对话型，阶段 3.1 ReactAgent 重构 + 4.x 改造 + 5.x 评估系统接入）
- ReactAgent（替代 ChatClient）：「思考→行动→观察」显式推理循环，MemorySaver 按 threadId=sessionId 隔离 checkpoint，单次运行结束 release
- 无 Advisor：RAG 检索、短期记忆读写、事实清单/计划/评估注入全是手动组装
- `chat(userMessage, sessionId, candidateId)` 新时序（5.3 起）：
  - 第 0 步：`ensurePlan`（5.2）→ `evaluateTurn`（5.3，评分落库 + 产注入文本）——评估必须在出题之前，结论才影响本题
  - 组装消息：薄弱点回顾(4.3) → 【面试计划】(5.2) → loadCodeFacts 清单 → searchKnowledge 题库 → 【上一题评估】(5.3) → 窗口历史 → 用户消息
  - 建 config 写入 metadata(candidateId) → `streamMessages` 流式 → 收尾写回窗口 + release
- **评分职责已移交（5.3）**：面试官不再打分落库（SYSTEM_PROMPT 原第 3 条"调 scoreRecord"与评分标准段已删除），改为转述【上一题评估】并按其"下题建议"调整本题难度方向——考官与评分分离是报告公信力的来源
- **SYSTEM_PROMPT 第 9 条（4.3）**：上下文带【跨会话薄弱点回顾】时——开局必须先点名薄弱考点、列为优先出题方向；用户说「继续上次的面试」→ 调 getWeaknessProfile 工具取；无注入时禁止虚构历史薄弱点（反幻觉护栏）
- **SYSTEM_PROMPT 第 10 条（5.2）**：带【面试计划】时按考点/优先级出题、优先覆盖未考察的高优先级考点、难度对齐考点难度档、不出计划外题目（求职者主动要求换题除外）
- `loadCodeFacts(sessionId)`：从 code_profile 表取事实清单 JSON 原文注入 system 消息（4.1 数据契约消费端）
  - **直接传原文、不做 Jackson 解析**：清单唯一读者是 LLM 且 LLM 读 JSON 是强项；只有"代码要程序化处理"才解析（判据：LLM 消费传原文、代码消费才解析）
- `getAgent()`：透出 ReactAgent 给编排器
- `sessionId` 不进模型可见参数：从 `RunnableConfig.threadId` 注入，工具经 `ToolContext` 取回，会话隔离最稳

**KnowledgeBaseService** —— 知识库同步
- `syncKnowledgeBase(resourceLocation, source)`：扫描 `*.txt` → 逐文件 `ingestFile` → `removeDeletedFiles` 增量删除
- `ingestFile`：读内容 → MD5 哈希 → 查 PG 元数据 → 哈希相同跳过（幂等）→ 变更/新增则 `TokenTextSplitter` 分块 → 带 `docId/chunkIndex` 元数据写入 Redis 向量库 → 更新 PG 元数据
- `deleteVectorChunks(docId, chunkCount)`：按 `docId_i` 拼 ID 删除向量块
- 分块器：`TokenTextSplitter` 默认 cl100k_base，约 800 token/块

### config

**AgentConfig**
- `chatMemoryRepository`：`JedisRedisChatMemoryRepository`（memory-redis starter 无自动装配，手动建 Bean，连接参数复用 `spring.data.redis.*`）
- `chatMemory`：`MessageWindowChatMemory`，maxMessages=60 滑动窗口（阶段 3 起不被 Advisor 自动注入，改由 InterviewAssistant 手动读写窗口）
- `memorySaver`：`MemorySaver` 内存版 checkpoint 保存器（RedisSaver 依赖 Redisson 客户端、与向量库强依赖的 Jedis 冲突，不用；单次运行结束即 release，不会无限累积）
- 阶段 3 起不再配置 `MessageChatMemoryAdvisor` / `QuestionAnswerAdvisor`：ReactAgent 不走 ChatClient  advisor，RAG 检索 / 记忆 / 清单注入全部由各 Agent 在 chat() 里手动做

**KnowledgeBaseLoader** —— `ApplicationRunner`，启动时自动加载
- 解析 `app.knowledge.path`（`file:./data/knowledges/`）
- 目录不存在 → 创建 + 回退 classpath；为空 → 回退 classpath；有文件 → 用外部题库
- 加载失败不影响应用启动（仅失去 RAG 能力）

**HttpClientConfig**
- `RestClient.Builder` 用 `JdkClientHttpRequestFactory`（非流式），`WebClient.Builder` 用 `JdkClientHttpConnector`（SSE 流式）
- 两者都改 JDK 客户端，彻底避开 Netty 异步 DNS 在某些网络环境超时（流式此前单独撞过此问题）

### tools

**SessionKeys** —— 身份 key 工具（4.2 新增 + 4.3 扩展，实测踩坑修复）
- `rootSessionId(ToolContext)`：取工具上下文里 RunnableConfig.threadId，在第一个 `_subgraph_` 处截断，返回根会话 id，取不到兜底 "unknown"
- 为什么需要：LlmRoutingAgent/SequentialAgent 派生子 Agent 时框架自动给 threadId 追加 `_subgraph_<agent名>` 后缀（实测日志/落库可见），直接当 sessionId 用会导致：①复用快路径 existsBySessionId(干净 id) 永远查不到带后缀记录 ②getCodeFacts 与落库 key 对不上 ③scoreRecord 落在带后缀 key 下，按 candidateId 聚合也会乱
- `candidateId(ToolContext)`（4.3）：从 RunnableConfig **metadata** 读候选人 id（入口 `addMetadata` 写入），取不到兜底 `DEFAULT_CANDIDATE_ID="default"`；candidateId 不拼进 threadId（threadId 会被子图加后缀、有框架语义，metadata 是业务自定义维度的干净去处）
- 所有 @Tool 工具统一经本类取身份键：业务隔离/聚合维度 = 根会话 id + 候选人 id

**InterviewTools** —— 面试官工具集（@Tool + @ToolParam 注解注册，身份键一律经 `SessionKeys` 从 `ToolContext` 取）
- ~~`scoreRecord(...)`~~（**5.3 删除**）：评分落库移交 AnswerEvaluatorService 代码侧执行——工具留着会造成"模型工具写 + 服务代码写"双写路径漂移；删掉后 score_record 唯一写入方收口（幂等/词表校验/钳制逻辑随迁）
- `questionStats(ToolContext)`：按**会话**聚合答题数/平均分/最低分，标注平均分<6 的薄弱考点
- `getWeaknessProfile(ToolContext)`（4.3）：按**候选人**跨会话聚合答题数/平均分/最低分，标注薄弱考点——委托 WeaknessProfileService（工具返回文本 = 开场注入文本，单一来源）；新面试开场回顾 / 用户说"继续上次的面试"时调用
- `calculator(values, op)`：纯函数计算（average/sum/percentage），避免模型算术幻觉
- `getCodeFacts(ToolContext)`：面试官**主动拉取**事实清单（含 CODE/JD/RESUME 三类，输出带资料类型标签）——在编排流水线里面试官作为子 Agent 跑，外层无法前置注入，只能靠 LLM 调工具取库（与 loadCodeFacts 前置注入互补：注入在重开场景、拉取在流水线场景）

**CodeAnalyzerTools** —— 分析官共用工具集（4.1 新增，4.2 加 type）
- `saveCodeProfile(filePath, factsJson, type, ToolContext)`：事实清单落库 code_profile；type 由模型按身份传 CODE/JD/RESUME，落库 profileType
- 为什么落库用 @Tool 让 LLM 自己触发：编排 Agent 自动按序执行子 Agent，外层没有"分析完、面试开始前"的中间钩子可插，所以由 LLM 分析完主动调工具落库（注意与 5.3 评估落库的区别：评估的输入/输出都是固定结构，代码可全权代劳；分析要 LLM 主动读文件，落库只能搭它的车）

### entity / repository

**CodeProfile**（PG 表 `code_profile`，4.1 新增 + 4.2 扩展）
- `id`(PK, 自增) / `sessionId` / `filePath` / `profileType`(CODE/JD/RESUME，4.2 新增，列默认 'CODE') / `factsJson`(text) / `createdAt`
- `factsJson` 存整段 JSON：代码产 techStack/designPatterns/implementationDetails/riskPoints/followUpPoints；
  JD 产 roleOverview/techRequirements/interviewFocus；简历产 skillProfile/projectHighlights/weaknessCandidates。
  JD/简历与代码共用一张表：三者同构（读资料→结构化清单），按 profileType 区分，面试官一次全取
- 数据契约物理载体：分析官写、面试官读，落库传递支持"重开会话不重复分析"

**InterviewPlan**（PG 表 `interview_plan`，5.1 新增）
- `id`(PK, 自增) / `sessionId`（一场面试一份计划） / `candidateId` / `topicsJson`(text) / `source`(JD=评分基准版 / USER=用户消息临时版) / `createdAt`
- `topicsJson` 结构：`[{"topic":"线程池参数","priority":"高","difficulty":"进阶"}, ...]`——**topic 字符串即主键语义**：评估归类、聚合统计、报告覆盖矩阵全部用这批字符串精确匹配（考点词表封闭，报告可 join 的前提）
- 为什么独立建表不复用 code_profile：计划是"一场面试的考核范围"，不是任何一份资料的画像；混表会让 loadCodeFacts 把计划当资料注入
- 一场一份、不做中途换计划：中途新考的领域按"计划外考点"如实进报告；唯一例外是 USER→JD 升级（见 InterviewPlanService）

**CodeProfileRepository**
- `findBySessionIdOrderByCreatedAtAsc`：按会话取全部清单（一个会话可能分析多个文件，合并出题）
- `existsBySessionId`：判断"该会话分析过没"——AgentRouter 复用快路径开关（5.5 泛化为"已分析 + 无新资料 → 直连面试官"）
- `existsBySessionIdAndProfileType`（5.5 新增）：按资料类型判断已分析——MaterialInterviewPipeline 复用路径按类生效；也是 InterviewPlanService USER→JD 计划升级的探测

**InterviewPlanRepository**（5.1 新增）
- `findBySessionId`：规划/面试官/评估官/报告四方共用的读取入口（ensurePlan 幂等的关键）
- `existsBySessionId`：廉价存在判断

**KnowledgeDocument**（PG 表 `knowledge_document`）
- `id`(PK, 自增) / `fileName`(唯一) / `chunkCount` / `contentHash`(MD5, 64) / `status`(枚举) / `source`(EXTERNAL/CLASSPATH) / `ingestedAt`
- 幂等比对靠 `contentHash` + `fileName`

**KnowledgeDocStatus**：`INGESTED` / `FAILED`

**KnowledgeDocumentRepository**：`findByFileName` / `existsByFileName` + JPA 基础方法

**ScoreRecord**（PG 表 `score_record`，4.3 加 candidateId 列）
- `id`(PK, 自增) / `sessionId` / `candidateId`(候选人身份键，4.3) / `topic`(考点) / `question` / `answer` / `score`(0~10) / `feedback` / `createdAt`
- 两把身份键分工：`sessionId` 管"这场面试"隔离（记忆/清单/统计），`candidateId` 管"这个人"跨会话聚合（4.3 薄弱点回顾）；一对多关系，同落一条记录
- 列不加 NOT NULL（存量历史数据兼容；新写入由工具保证带值，查询侧不依赖该约束）
- `createdAt` 由服务端落库时生成，不依赖 LLM 传时间
- 题目文本直接冗余存储，不建外键关联题库文档（题库文档会被增量清理，外键反而埋隐患）

**ScoreRecordRepository**
- `findBySessionIdOrderByCreatedAtAsc` / `findBySessionIdAndQuestion`（幂等去重）/ `aggregateByTopic`（GROUP BY 考点聚合，会话维度）
- `aggregateByTopicForCandidate(candidateId)`（4.3）：同一条聚合 SQL 只换 WHERE 维度（`sessionId` → `COALESCE(candidateId,'default')`，老数据 NULL 归到默认候选人），返回结构不变（[topic,count,avg,min]），消费端复用同一套解包

## 4. API 契约表

| 方法 | 路径 | 入参 | 返回 | 说明 |
|---|---|---|---|---|
| POST | `/api/assistant/chat` | body `{userMessage, sessionId, candidateId?}` | `text/event-stream`（`Flux<String>`） | 面试对话，SSE 流式（chat 契约 5.x 零改动，前端零改动） |
| GET | `/api/assessment/{sessionId}/report` | query `candidateId?` | 报告 JSON：plan / coverage(含证据链) / uncoveredTopics / outOfPlanTopics / crossSessionWeakness / conclusion | 《面试评估报告》（5.4），同步非流式，无副作用可重复调用 |
| GET | `/api/assistant/memory` | - | `string[]` | 所有会话 id |
| GET | `/api/assistant/memory/{sessionId}` | path | `[{role,content}]` | 会话历史（滑动窗口内） |
| DELETE | `/api/assistant/memory/{sessionId}` | path | `{sessionId,cleared}` | 清空会话 |
| POST | `/api/knowledge/sync` | - | `{message,totalDocuments}` | 手动同步知识库 |
| GET | `/api/knowledge/documents` | - | `[{fileName,chunkCount,status,source,ingestedAt}]` | 文档元数据列表 |

> 默认 `sessionId=default`。`candidateId` 可选（4.3）：不传或空串 → 兜底 `"default"`（所有会话归同一候选人，跨会话薄弱点回顾立即可用）；传不同值可模拟多候选人。
> SSE 数据为纯文本分片（`Flux<String>`），前端按 text/event-stream 增量拼接。
> ⚠️ Spring 的 SSE 写出器会自动把分片内 `\n` 转成 `\ndata:` 续行（**控制器切勿再手动转义**，否则双重转义会在页面混入多余的 `data:` 文字）；前端 `sse.ts` 把同帧多条 `data:` 行按 `\n` 拼接还原换行，否则换行全丢、回答挤成一段。

## 5. 数据存储说明

### Redis Stack（6379，可视化 8001）

- 表 `knowledge_document`（JPA `ddl-auto=update` 自动建/改）：题库文档元数据
- 表 `score_record`：单题评分记录（阶段 2.3；5.3 起唯一写入方 = AnswerEvaluatorService，字段见上「ScoreRecord」）
- 表 `code_profile`：代码分析事实清单（阶段 4.1），字段见上「CodeProfile」
- 表 `interview_plan`：面试计划（阶段 5.1），字段见上「InterviewPlan」

## 8. 关键风险 / 注意点

1. **Redis 必须 Stack 版**（普通 Redis 无 RediSearch 向量模块，报 `unknown command 'FT._LIST'`）
2. **向量库强依赖 Jedis**：`spring.data.redis.client-type=jedis` + `commons-pool2`，否则 `VectorStore` Bean 创建失败
3. **Windows 中文 JVM 默认 GBK** → 中文乱码：`.mvn/jvm.config` 已加 `-Dfile.encoding=UTF-8`（作用于 Maven 本体）→ **fork 出的应用进程不继承它**，必须再在 `spring-boot-maven-plugin` 配 `<jvmArguments>-Dfile.encoding=UTF-8</jvmArguments>`（4.1 验收实测踩坑）；IDEA 运行配置 VM options 也要加
4. **向量维度对齐**：qwen3.7-text-embedding 默认 1024 维，与索引一致；换模型/改 dimensions 需先查索引维度
5. **6379 抢占**：本机若有原生 Redis 会抢占端口且无向量模块，需 `net stop Redis`
6. `initialize-schema: true` 首次启动建索引，之后可改 false
7. API Key 开发期硬编码，公开仓库前移到环境变量并去百炼控制台重置（旧 key 已在 git 历史里）
8. PG 连接信息以根目录 `docker-compose.yml` 为准（admin/admin123，库 aiagent）
9. 外部知识目录 `data/knowledges/` 默认 gitignore，示例题库放 `resources/knowledges/` 兜底
10. 每个阶段结束 git commit，方便简历展示 commit 历史
11. **SSE 流式走 WebClient**：若流式接口报错，先排查 DNS——`RestClient`（非流式）和 `WebClient`（流式）要分别覆盖，`HttpClientConfig` 两者都改 JDK 客户端已规避
12. **Function Calling 需验证 SSE 流式下的工具触发**：Spring AI 流式默认会执行工具调用并回填，但工具触发的中间 token 会混进流，前端按 SSE 拼接时无需特殊处理
13. **模型重复调用工具**：同一道题可能被多次落库，`scoreRecord` 已按 `sessionId+question` 幂等去重
14. **MCP 管道编码坑（兼容 3，4.1 验收实测）**：应用 JVM 若不是 UTF-8，`read_file` 返回的中文注释会被 GBK 误解码，乱码中恰好吞掉 JSON 引号 → `JsonParseException` → MCP 通道瘫痪、后续工具全部 60s 超时。症状像"MCP 超时"，根因是编码，先查 JVM `file.encoding` 再怀疑 MCP 本身
15. **SequentialAgent 流式会混入分析官输出（计划书风险 14 实测确认）**：`pipeline.streamMessages()` 会把分析 Agent 的思考文字也流给前端（用户会先看到"让我再读取……"的分析过程再看到题目）。不影响功能；4.2 并行场景三路分析的文字会一起混进来，实测属预期行为，未做过滤
16. **路由是 LLM 概率决策 + fallback**：意图分类不保证 100% 准确（实测波动），`fallbackAgent` 必须指向面试官；测试时注意用 UTF-8 文件发中文（curl -d 内联中文在 Git Bash 会以 GBK 发出导致 400 `Invalid UTF-8 start byte`，这是测试脚本坑，不是服务端 bug）
17. **子图 threadId 后缀（4.2 验收实测）**：LlmRoutingAgent/SequentialAgent/ParallelAgent 派生子 Agent 时框架自动给 threadId 追加 `_subgraph_<agent名>`（可多层嵌套叠加），子图内 @Tool 直接拿到的 threadId 带后缀，会打破会话隔离（复用快路径失效、getCodeFacts 取不到、scoreRecord 错 key）。已用 `SessionKeys.rootSessionId()` 统一归一化
18. **ParallelAgent 输出键约束（4.2 验收实测）**：并行子 Agent 不设 `outputKey` 会打警告（合并拿不到数据）；设了相同值会被校验拒绝（`Duplicate output keys found among sub-agents`）。每个子 Agent 用唯一 outputKey（本项目用 name），合并策略才会有数据
19. **分析官 LLM 可能漂移（4.2 实测）**：prompt 没写硬性约束时，代码分析官曾跑去 directory_tree 浏览、且不调 saveCodeProfile 就结束（DB 缺条）。已加"只用 read_text_file / 只读自己的文件 / 最后一步必须落库"三条硬性要求后稳定。教训：结构化执行的 prompt 必须约定"失败判据"，且数据传递不要只依赖一条路（DB + 状态消息双路）
20. **换模型 = 换 API 契约（4.2 课后实测）**：对话模型从 qwen3.7-plus 切到 kimi-k3 后，DashScope 兼容端点报 `temperature=0.7 is not supported for kimi-k3`——框架默认参数 ≠ 所有模型接受。修复：`OpenAiModelConfig` 自定义 ChatModel，OpenAiChatOptions 不设 temperature（ChatCompletionRequest 带 @JsonInclude(NON_NULL)，null 时省略）。换任何模型都要先实测第一个请求
21. **fallbackAgent 只兜"选错人"不兜"服务挂"（4.2 课后实测）**：路由 LLM 返回无效名字时框架重试后走 fallbackAgent；但模型 API 硬异常（如 429 限流）会直接 500，fallback 不介入。面试问"兜底到底兜什么"时可精确回答
22. **saveCodeProfile 无幂等键（4.2 课后实测）**：分析官可能对同一资料重复调用落库（实测 JD 存 2 条），与 scoreRecord 的 `sessionId+question` 幂等不同，code_profile 无去重键；不影响功能（清单依旧可读），如需严格去重可按 filePath+type+hash 加键
23. **flash 模型对 scoreRecord 的工具调用遵从度低（4.3 验收实测）**：qwen3.7-flash 评分时多次"用嘴打分、不落库"（把「本题评分：3/10」直接写进文本、不调 scoreRecord，日志无 `工具调用 scoreRecord`），显式命令（把 topic/question/answer/score/feedback 参数喂全）后才触发。现象与他类"分析官漂移"同源（工具调用是概率决策）。对演示/验收的影响：靠普通对话攒评分记录可能落不了库；对策：换遵从度更高的模型（qwen3.7-plus）或在 SYSTEM_PROMPT 强化"评分=调工具，禁止以文本代替"。注意这不影响 4.3 链路本身（calculator/getWeaknessProfile/scoreRecord 在流式子图下均实测可触发）。**5.3 已结构性修复**：评分落库改为 AnswerEvaluatorService 代码侧执行，scoreRecord 工具删除——本条保留作历史档案与面试谈资
24. **评估官自门控与降级（5.3 设计）**：是否评分由 LLM 结构化输出的 isAnswer 决定（寒暄/反问/请求换题不算作答）；JSON 解析失败重试 1 次后降级为"本轮不评分不注入"（WARN），面试不阻塞——评估是增强项不是阻塞项，与"计划生成失败跳过注入"同一降级哲学
25. **每轮 +1 次 LLM 调用（5.3 设计）**：评估在流式出题前同步执行，首 token 延迟约 +1~2s；后续优化方向：评估与 RAG 检索并行化（两者互不依赖）、评估模型降档
26. **资料规则误报靠守门兜底（5.5 设计）**：detectMaterials 关键词命中（如"岗位"）不代表资料真在场——误报时对应分析官由【资料守门】拦住直接跳过不落库；反向的语义表述漏报（无路径无关键词）由 LlmRoutingAgent 语义路由兜住。规则管确定的事，LLM 管语义的事，守门管两边都错的事
27. **面试计划 USER→JD 升级语义（5.2 设计）**：综合面试首轮只有按用户消息生成的临时计划（source=USER），JD 画像落库后下一轮 ensurePlan 自动升级重生成（source=JD）；覆盖矩阵以最终 JD 计划为基准，临时计划期的首题若不在最终词表内按"计划外"如实呈现——宁可在报告里诚实标注，不做静默改约
28. **scoreRecord 评分列长截断防御（5.3 设计）**：评估落库侧对 topic(64)/question(2000)/answer(4000)/feedback(2000) 统一截断（旧工具链路由模型填参、长度靠模型自觉）；上一问取窗口尾部截断（题目通常在助手消息后半段）、回答取头部截断
