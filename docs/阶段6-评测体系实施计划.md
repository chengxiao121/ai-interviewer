## 1. 背景与动机

**简历深挖点没有数据支撑。** 简历 RAG 条目写明了召回机制（topK=3、相似度阈值 0.7），这两个数是本项目简历上最可能被面试官深挖的技术点。当前它们的来源是"经验初始值 + 人工抽测"，没有系统性的数据支撑——面试官一旦追问"0.7 怎么定的？凭什么"，只能回答方法论而不能给出实测结论。

**阶段 6 需要一块地基。** 后端架构进度表里阶段 6「测量（eval harness）」仍为空白。本次评测构造的查询-标注数据集与测量代码，就是 eval harness 的第一块骨架，后续阶段 6 全量评测（路由/评分一致性等）在此基础上扩展，不用从零开始。

**目标：** 用约 40~60 条带标注的查询 + 网格扫描，回答三个问题：

1. 当前配置 (topK=3, 阈值=0.7) 的检索质量到底如何（召回率、噪音、空命中）？
2. 阈值和 topK 的参数曲面长什么样，0.7 是偏严还是偏松？
3. 有没有更好的工作点？若调整，依据是什么？

## 4. 数据集设计（评测"测哪些方面"的依据）

### 4.1 规模与来源（约 40~60 条）

- **题库为主（约 30~45 条）**：从 16 道题中每道生成 2~4 个问法——真题措辞、口语化问法、同义改写（覆盖"同题不同问法"的鲁棒性验证）。
- **掺真实语料（约 10~20 条）**：从 `.verify-payloads/*.json`、`test-http/r1~r3.json` 提取真实用户提问原话；从 `test-http/app-run.log` 的 `potentialQuestions`/`followUpPoints`/`verifyQuestion` 字段提取面试官真实追问原文。

### 4.2 标注规则

- 每条 query 标注**相关 chunk 集合**（`chunkId` 形如 `java-interview-questions.txt_0`）。
- 小库（16 题、约十数个 chunk）下可逐条精确标注；同文件同章节内相邻 chunk 视为相关。
- 流程：先执行一次入库同步拿到**实际 chunk 清单**，再据清单精标；标注结果给项目所有者复核一遍（约 10 分钟）。

### 4.3 数据集文件

`src/main/resources/eval/queries.json`，结构：

```json
[
  {
    "id": "q001",
    "query": "考我一道 Java 并发题",
    "source": "real-payload",
    "relatedChunks": ["java-interview-questions.txt_3", "java-interview-questions.txt_4"]
  }
]
```

`source` 取值：`topic`（题库问法）/ `real-payload`（真实请求）/ `real-log`（真实日志追问）。

## 5. 指标定义（评测哪些方面）

| 方面 | 指标 | 定义 / 业务意义 |
|---|---|---|
| 召回 | Recall@K | 检索返回的前 K 个中，与标注相关的数量 / 标注相关总数。测"该命中的有没有命中" |
| 召回 | Hit@1 / Hit@K | 至少一个相关 chunk 出现在 top1 / topK 的 query 占比。测"要不要被别人继续问才有答案" |
| 排序 | MRR | 第一个相关 chunk 排位的倒数均值。测"正确答案排得有多靠前" |
| 阈值行为 | 空命中率 | 相关 chunk 全部被阈值滤掉（或返回空）的 query 占比。**0.7 偏严的直接证据** |
| 阈值行为 | 噪音率 | 返回结果中无关 chunk 占比。**阈值偏松/上下文被污染的直接证据** |
| 鲁棒性 | 改写稳定性 | 同一知识点不同问法的得分离散程度。测"query 是用户整句话"这个设计靠不靠谱 |

> 小库注意：topK 较大时（如 10）会返回全库大部分 chunk，尾部饱和属预期行为，报告解读时注明。

## 6. 扫描方案与成本分析

- **网格**：阈值 ∈ {0.50, 0.55, …, 0.95}（10 档）× topK ∈ {1, 2, 3, 5, 10}（5 档）= **50 组**。
- **成本**：每条 query 的**向量只嵌入一次**（约 50 次调用，DashScope 费用几分钱量级）；之后所有 50 组参数组合都只是对已嵌入向量做本地 Redis 向量检索（免费、毫秒级）。**扫描本身几乎没有边际成本。**
- **范围说明**：本次只扫 topK + 阈值（项目所有者已确认范围）；分块参数扫描需重建索引、重嵌全库，列为后续可选项（§9）。

## 7. 实施步骤

1. **环境验证**：`docker compose ps`（Redis Stack / PG 均 Up）→ `redis-cli ping` → 调一次 embedding 确认 key 与 quota。任一失败则暂停并回报。
2. **入库取 chunk 清单**：触发知识库同步（启动 / `POST /api/knowledge/sync`），拿到实际 chunk 清单（文件 × 序号），作为标注底版。
3. **构建数据集**：按 §4 生成 queries.json；标注清单给项目所有者复核。
4. **实现测量程序** `src/main/java/com/xiao/aiagent/eval/RagEvalRunner.java`：
   - 加载 queries.json，逐一 embedding（一次）；
   - 双层循环扫描 50 组参数，每组对每条 query 跑 `VectorStore.similaritySearch`；
   - 计算 §5 全部指标，输出 metrics.csv + markdown 报告。
   - 运行：`mvn spring-boot:run -Dspring-boot.run.main-class=com.xiao.aiagent.eval.RagEvalRunner`（或 IDE 直跑 main）。
5. **扫描并分析**：记录当前配置 (3, 0.7) 为基线；找阈值拐点（召回上升趋缓 / 空命中率飙升处）与 topK 饱和点；给推荐参数。
6. **收尾**：结论回填本文档「结果」章节；汇总一句带真实数字的面试话术供简历参考。
7. **（可选，需另行确认）**参数采纳：是否将推荐参数写入 `KnowledgeSearchService`，由项目所有者决定后单独实施。

## 8. 验收标准

1. 本文档完整落盘，评测范围与标注规则可复述。
2. 数据集 ≥40 条，含真实语料条目，标注经复核。
3. 50 组指标全量可复现（给出一次跑通的运行命令）。
4. 报告给出：基线 (3, 0.7) 指标、阈值-召回/空命中/噪音曲线、topK 饱和点、推荐参数及理由。
5. 现有运行代码零改动（除新增数据集与测量程序文件外）。

## 9. 后续扩展（阶段 6 全量 eval 的衔接路径）

- **分块参数扫描**（第二步可选项）：chunkSize 100/200/300/500 × overlap 0/50/100，需重建索引并重嵌全库（+1~2 小时）。分块对检索质量影响通常大于 topK/阈值，是深挖时的加分点。
- **路由准确率评测**：语义路由对"看代码/直接出题/闲聊"的分类准确率与误路由率。
- **LLM 评分一致性**：评估模块打分与人工评分的对齐程度（LLM-as-judge 一致性）。
- **回归保护**：把本轮数据集固化，后续任何检索相关改动跑一遍对比，防止修 A 坏 B。

## 10. 风险与注意

1. **知识库极小**（~16 题、~7.7KB）：topK 大时饱和属预期，报告注明；若后续题库扩充，评测结论需重跑确认。
2. **标注质量**：半自动标注，须人工复核（本项目所有者 10 分钟），否则指标会被标注噪声污染。
3. **Windows 编码**：所有读写按 UTF-8（仓库 jvmArguments 已处理；Git Bash 终端直读中文会乱码属显示层错觉，以 UTF-8 解码为准）。
4. **外部 API 依赖**：嵌入调用走 DashScope，断网/限流时先验证 key 与 quota。
5. **不要擅自改参数**：改 `KnowledgeSearchService` 会改变真实面试输出行为，必须另行确认后实施。
