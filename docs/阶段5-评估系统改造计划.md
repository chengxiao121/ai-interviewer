## 0. 背景与目标

### 0.1 叙事定位（一句话，README/简历/面试通用）

> 输入 JD/简历/代码 → 多 Agent 并行画像 → **按计划**实时自适应考核 → 输出**带证据链**的《面试评估报告》。

### 0.2 目标形态：plan → execute → verify → report

```
面试开始前   规划（InterviewPlanService）   ← JD 考察矩阵 / 用户指定领域 → 《面试计划》落库
    ↓
面试执行中   考核（面试官，按计划出题）
             评估（AnswerEvaluatorService）← 每轮答完即评分落库 → 下一题当场调整难度（会话内闭环）
    ↓
面试结束时   报告（AssessmentReportService）← 计划 vs 实际覆盖对照 → 《评估报告》（独立端点）
```

与现状（4.3）的本质区别：反馈闭环从"**跨会话**"缩到"**跨单题**"；
交付物从"无"变成"可下载、可第三方校验的结构化报告"。

### 0.3 核心判据：LLM 调用 ≠ Agent

| 新增环节 | 需要工具循环/临场决策？ | 实现形态 |
|---|---|---|
| 规划 | ❌ 输入（JD 画像/用户消息）固定 → 输出（计划 JSON）固定 | **Service 方法 + 一次 LLM 调用** |
| 评估 | ❌ 输入（上一问+本轮回答）固定 → 输出（结构化评估）固定 | **Service 方法 + 一次 LLM 调用** |
| 报告 | ❌ 输入（计划+全部评分）固定 → 输出（报告 JSON）固定 | **Service 方法 + 一次 LLM 调用**（只写叙事） |

**真 ReactAgent 数量保持 4 个不变**（面试官 + 三个分析官）。规划/评估/报告不做成 Agent
的理由：给不需要决策的环节上 ReactAgent（工具循环 + checkpoint）是纯粹的膨胀与漂移面。

## 1. 设计原则（4 条，实施中所有取舍按此裁决）

1. **只有需要工具循环的环节才配 ReactAgent**；固定输入→固定结构化输出的一律是 service 方法。
2. **落库由 Java 代码做，不由 LLM 工具做**：评分落库从"面试官调 scoreRecord 工具"改为
   "评估 service 解析结果后直接 save"。结构性修掉风险 23（flash 用嘴打分不落库）——
   漂移面从"长对话中间的一次概率性工具调用"缩成"独立单轮结构化输出 + 代码侧确定性落库"。
3. **考点词表封闭**：评估产出的 `topic` 必须取自《面试计划》的考点列表（Java 侧校验，
   兜底归类"计划外"）。这是覆盖率可验证的前提——自由文本考点无法与计划做 join。
4. **数字由代码算，叙事由 LLM 写**：报告中的统计数字（题数/均分/覆盖数）全部由 Java 聚合
   （复用 `aggregateByTopic` 系 SQL），LLM 只在"给定数字"的前提下写总结/建议。
   反幻觉护栏与 4.3"无注入不虚构"同一逻辑。

附带判据沿用现有约定（`InterviewAssistant.loadCodeFacts` 注释）：**LLM 消费传原文、
代码消费才解析**——计划/评估/报告的输出都会被代码程序化处理（校验/落库/join），
故一律 JSON 解析成 DTO；坏 JSON 重试一次，仍失败则降级跳过（不阻塞面试）。

## 2. 架构变化

```
改造前                                     改造后
──────────────────────────                ──────────────────────────
POST /api/assistant/chat                  POST /api/assistant/chat            （契约不变，前端零改动）
  └ LlmRoutingAgent（3 路）                 └ AgentRouter 三道关口（阶段 5.5）
      ├ code-review-pipeline                   ├ ① 复用快路径（已分析+无新资料 → 直连面试官）

      └ interviewer                            └ material-interview = MaterialInterviewPipeline
            └ 面试官 chat()：                       （收敛两套流水线：Parallel(选中的分析官×N) → 面试官）
              组装上下文 → 出题（自带评分落库）

                                              ① ensurePlan（无计划则规划落库）

GET /api/assessment/{sessionId}/report  →  AssessmentReportService → 报告 JSON
```

**Agent 盘点（改造前后对比）**

| 角色 | 改造前 | 改造后 |
|---|---|---|
| 真 ReactAgent | 4（面试官 + 分析官×3） | **4（不变）** |
| 路由 Agent | 1（3 路） | 1（2 路 + 规则前置） |
| 编排流水线类 | 2（CodeReview/Combined） | **1（MaterialInterviewPipeline）** |
| LLM service 函数 | 0 | 3（规划/评估/报告，各几十行） |

## 阶段 5.1 —— 数据契约改动

> 提交：`阶段5.1：数据契约——interview_plan 计划表`。验收：启动建表成功；手工 insert/select 通过。

### 新表 `interview_plan`（InterviewPlan 实体 + InterviewPlanRepository）

| 列 | 类型 | 说明 |
|---|---|---|
| id | PK 自增 | |
| sessionId | varchar(64), 不可空 | 一场面试一份计划（本节约定：不做会话中途换计划） |
| candidateId | varchar(64) | 与 score_record 同口径，报告侧跨会话分析预留 |
| topicsJson | text | 考点数组 JSON，见下 |
| source | varchar(16) | 计划来源：`JD`（有 JD 画像）/ `USER`（仅用户消息推断） |
| createdAt | timestamp | 服务端生成 |

`topicsJson` 示例（封闭词表的物理载体，评估/报告两侧的 join 键）：

```json
[
  {"topic": "线程池参数",   "priority": "高", "difficulty": "进阶"},
  {"topic": "synchronized 与 Lock", "priority": "中", "difficulty": "基础"},
  {"topic": "AQS 原理",     "priority": "低", "difficulty": "挑战"}
]
```

约定：**topic 字符串即主键语义**——评估落库、聚合统计、报告覆盖矩阵全部用这批字符串精确
匹配（不做向量化/模糊化）。Repository 方法：`findBySessionId` / `existsBySessionId`。

### `score_record`：不改 schema，改写入方与取值约定

- 列结构零改动（topic 列沿用，长度 64 足够）。
- **写入方变更**：`scoreRecord` @Tool 删除（见阶段 5.3），落库改由 `AnswerEvaluatorService` 代码执行；
  幂等去重沿用 `findBySessionIdAndQuestion`（同会话同题更新不新增）。
- **topic 取值变更**：新数据一律从计划词表取（Java 校验）；历史数据的自由文本 topic
  在报告 join 时做包含匹配 best-effort（见 §8 风险 7）。

### `code_profile`：不动

JD/简历/代码三类画像照旧。规划官是 JD 画像的**消费方**（读 `profileType=JD` 的 factsJson）。

### 落地文件

`entity/InterviewPlan.java`、`repository/InterviewPlanRepository.java`（新增）；
`CodeProfileRepository.existsBySessionIdAndProfileType`（新增方法，阶段 5.5 按类复用 + 阶段 5.2 升级探测共用）。

## 阶段 5.2 —— 面试规划（InterviewPlanService）

> 提交：`阶段5.2：规划官 InterviewPlanService`。验收：新会话首题前日志可见计划落库；连续出题命中计划考点；生成失败时面试不中断。

### 服务设计

```
职责：为一场面试产出《面试计划》（考点清单 + 优先级 + 难度档），落库 interview_plan。
签名：InterviewPlan ensurePlan(String userMessage, String sessionId, String candidateId)
触发：面试官 chat() 首步 & 流水线上下文装配（§6）；已有计划直接返回（幂等，每轮只花一次索引查询）。
输入：① 该会话 code_profile 中 profileType=JD 的画像（有则作为主依据，source=JD）
      ② 用户消息（无 JD 画像时从"来一场 Java 并发面试"提取领域，source=USER）
输出：DTO `PlanTopic[] {topic, priority(高/中/低), difficulty(基础/进阶/挑战)}`，3~6 个考点，
      Jackson 解析（代码要校验词表，必须解析）。
Prompt 要点：
      - 输入 JD 画像时：interviewFocus 的每一条必须落成一个考点，不许漏；
      - 输入仅用户消息时：围绕该领域出 3~6 个由浅入深的考点；
      - 只输出 JSON 数组，禁止解释性文字。
失败降级：解析失败重试 1 次 → 仍失败返回 null（跳过计划注入，面试照常，记 WARN）。
      计划是增强项不是阻塞项——出题本身不依赖计划也能跑（与"题库检索不到就跳过"同模式）。
```

三个消费方：面试官（`renderPlan` 渲染【面试计划】system 注入，**每轮注入**——文本只有几行，
成本可忽略，换来"模型每轮都被拴在计划上"）/ 评估官（`parseTopics` 取封闭考点词表）/ 报告（覆盖矩阵对照基准）。

### 配套改动

- `StreamingPipelineSupport.buildChatMessages`：薄弱点注入之后增加【面试计划】注入——
  流水线路径的面试官子 Agent 同样吃到计划，"一处改动多路生效"沿用既有模式。
- 面试官 `SYSTEM_PROMPT` 新增第 10 条：带【面试计划】时按考点/优先级出题、优先覆盖未考察的
  高优先级考点、难度对齐考点难度档、不出计划外题目（求职者主动要求换题除外）。
- 落地文件：`services/InterviewPlanService.java`、`services/LlmJson.java`
  （LLM 结构化输出清洗：剥围栏 + 截 JSON 本体，规划/评估/报告三处共用）。

## 阶段 5.3 —— 答案评估（AnswerEvaluatorService）

> 提交：`阶段5.3：评估官 AnswerEvaluatorService`。核心验收：答砸（3 分）→ 下一题**当场**换角度/降难度（4.3 需跨会话才能演示）；日志确认落库由 service 打出（无 `工具调用 scoreRecord`）；寒暄轮不产生评分记录。

### 服务设计

```
职责：每轮判断"这句回答答的是上一道题吗"，是则评分、落库、产出给面试官的下题调整建议。
签名：EvaluationOutcome evaluateTurn(String userMessage, String sessionId, String candidateId, InterviewPlan plan)
      EvaluationOutcome { boolean answered; String injectionText; }
触发：InterviewAssistant.chat() 第 0 步（§6 时序），每轮必调——**确定性触发，不靠模型自觉**。
自门控（在 prompt 内完成，替代脆弱的正则启发式）：
      输入 = 窗口最后一条 AssistantMessage（视为"上一问"）+ 本轮 userMessage + 计划词表；
      输出 JSON = { isAnswer, topic, question, score, strengths, gaps, nextSuggestion }
      - isAnswer=false（寒暄/提问/请求跳过）→ 不落库，返回空注入文本；
      - isAnswer=true → topic 必须从计划词表选（Java 校验：精确匹配 → 包含匹配归一 →
        兜底记"计划外：<原文>"），service 代码直接 save score_record（幂等同「阶段 5.1」节）。
注入文本格式（injectionText，进 system 消息）：
      【上一题评估】考点：线程池参数；得分：3.0/10；薄弱：未答出核心参数含义；
      下题建议：换更基础的角度或换考点。→ 面试官据此当场调整本题难度/方向。
追问语义：追问也是"一问"，逐答逐评；同考点多次答题在聚合中自然累加，报告如实呈现。
为什么放在面试官 chat() 内而不是流水线图里：
      流水线场景面试官只在首 turn 作为子 Agent 跑（首问无答案可评）；后续每一轮对话
      都会流经 InterviewAssistant.chat()（直连快路径或路由 interviewer），评估挂在这里
      = 全场景覆盖 + 单点实现。
```

### 配套改动

- `InterviewAssistant.chat()`：时序前置（评估先于出题，见 §6）+ 注入 `AnswerEvaluatorService`。
- `InterviewTools`：**删除 `scoreRecord` 工具**——工具留着会造成"模型工具写 + 服务代码写"
  双写路径漂移；删掉后 score_record 唯一写入方收口到评估服务（§1 原则 2）。
- 面试官 `SYSTEM_PROMPT`：第 3 条改为"转述【上一题评估】并按其下题建议调整本题"，文末
  "评分标准（0~10 分）"整段删除（评分职责唯一归属评估官，评分标准迁入评估 prompt）。

## 阶段 5.4 —— 评估报告（AssessmentReportService + AssessmentController）

> 提交：`阶段5.4：评估报告`。验收：curl 出报告 JSON，覆盖矩阵数字与库中聚合一致（SQL 对账）；有未覆盖考点时 uncoveredTopics 非空；无计划会话可出降级版报告。

### 服务设计

```
职责：对照《面试计划》核查实际覆盖，产出可校验的《面试评估报告》JSON。
签名：ReportResult generate(String sessionId, String candidateId)
输入：interview_plan + score_record（本会话全部）+ WeaknessProfileService（跨会话薄弱点）
分工（§1 原则 4）：
      Java 算数字：逐考点 {是否在计划内, 答题数, 平均分, 最低分, 证据[]（题目/回答节选/得分/点评）}、
                   未覆盖考点（计划有、实际 0 题）、计划外考点（实际有、计划无）；
      LLM 写叙事：一次调用，输入=上述计算结果 JSON，输出={overallSummary, matchConclusion,
                   recommendations[]}——只许解读给定数字，禁止自造数字（prompt 明令 + 幻觉即报告失真）。
输出 JSON 顶层结构：
      { sessionId, candidateId, generatedAt,
        plan:   {source, topics:[{topic, priority, difficulty}]},
        coverage:[{topic, planned, questionCount, avgScore, minScore,
                   evidences:[{question, answerExcerpt, score, feedback}]}],
        uncoveredTopics:[...], outOfPlanTopics:[...],
        crossSessionWeakness: "（WeaknessProfileService 文本，可空）",
        conclusion: {overallSummary, matchConclusion, recommendations[] } }
无计划时降级：coverage 退化成"仅实际考点统计"，plan/uncovered 置空（报告仍可出，注明无计划基准）。
```

### 配套改动

- 新增 `controller/AssessmentController.java`：`GET /api/assessment/{sessionId}/report?candidateId=`，
  同步非流式返回报告 JSON——报告是交付物不是对话流，独立端点、不进聊天路由
  （寒暄永远不会被误分到"生成报告"）；无副作用可重复调用，故用 GET。
- `AssistantController` 与 chat 契约**不动**（前端零改动）。

## 阶段 5.5 —— 流水线收敛与路由改版

> 提交：`阶段5.5：流水线收敛`。验收：三种输入各自正确装配（只给代码→1 分析官；JD+简历→2；三者→3）；原 code-review/combined 表述的消息路由不回归；单会话二轮对话不再触发重复分析。
> ⚠️ 本节与原计划有实施偏差（"计划先于第一题"改临时计划+升级、新增规则前置与资料守门），落地实况见 **§11**。

### MaterialInterviewPipeline（合并 CodeReviewPipeline + CombinedInterviewPipeline）

两套旧流水线是同一模式（"分析官产物料 → 面试官消费"）的两份拷贝，唯一区别是分析官个数；
收敛后分析官集合是参数——用户给了什么资料就挂什么分析官，任意组合开箱即用。

- 结构两层：`SequentialAgent( ParallelAgent(选中的分析官×N), interviewer )`（编排管时序、数据走 code_profile 落库）。
- `detectMaterials(userMessage)`（静态规则）：code=盘符/扩展名/评审关键词（自旧 isCodeReviewRequest 迁移），
  JD=岗位/JD/职位，简历=简历/resume/CV；三类独立检测、可叠加。
- 复用按类生效：只对"库里还没有对应 profileType 清单"的资料跑分析官；全部已分析 → 直连面试官。
- 按组合缓存构建：bitmask（CODE=1/JD=2/RESUME=4）为键，最多 8 种组合，computeIfAbsent。
- `getPipeline()` 透出【全量组合】图给路由注册——路由 LLM 只判断"是不是资料面试"，
  缺哪类资料由分析官【资料守门】运行时自筛。

### AgentRouter 三道关口（3 路并 2 路 + 规则前置）

1. **复用快路径**：已分析过 + 本条消息无新资料 → 直连面试官（跳过一切）；
2. **规则路径**：detectMaterials 命中 → 直接进流水线（组合判断确定性 100%，省路由 LLM）；
3. **语义路由**：LlmRoutingAgent 两选一（material-interview / interviewer），fallback=interviewer——
   只兜规则漏掉的语义表述（"帮我看看上周写的那个线程池"）。

### 分析官【资料守门】（ProfileAnalyzerAgent）

基类统一把守门条款拼进每个分析官 systemPrompt：上下文没有自己负责的资料 → 直接结束、
禁止调工具、禁止落库、禁止编造。兜住规则误报与全量组合下的"缺类"，把"没资料"变成显式且极简的执行路径。

## 8. 风险预判（实施时逐条核对）

1. **评估官自身漂移**（flash 结构化输出遵从度，风险 23 同源）：JSON 解析失败重试 1 次，
   仍失败降级为"本轮不评估"（WARN + 跳过注入），面试不中断——评估是增强项不是阻塞项。
2. **每轮 +1 次 LLM 调用**：首 token 延迟 +1~2s、token 成本上升。用同一 flash 模型；
   后续可选：评估模型降档 / 与 RAG 检索并行化（两者互不依赖）。
3. **考点词表漂移**：评估返回的 topic 不在词表 → Java 侧精确匹配 → 包含匹配归一 →
   兜底"计划外：<原文>"三级策略；报告如实呈现计划外，不改写数据。
4. **会话中途换话题**：v1 不做动态改计划，换的领域按"计划外考点"进报告（诚实呈现优于
   静默改约）；若实测高频，再立"计划更新"需求。
5. **流水线拆段后直连面试官**：不经子图时 threadId 无 `_subgraph_` 后缀，
   `SessionKeys.rootSessionId` 的截断逻辑需验证对"无后缀"入参无副作用（预期：找不到
   分隔符原样返回）。
6. **prompt 回归**：面试官 SYSTEM_PROMPT 删评分段时，寒暄（8）/URL（6）/清单（7）/
   薄弱点（9）各条保持原文不动，改完通读一遍防止编号断链。
7. **存量数据兼容**：历史 score_record 的自由文本 topic 与新词表 join 不中 → 报告侧
   包含匹配 best-effort，仍不中计入"计划外/历史数据"，不阻塞报告生成。
8. **路由回归（阶段 5.5）**：三路并两路后，用原验收消息（"考我一道并发题"/"评审我的代码"）
   回归分诊正确性；fallbackAgent 仍指向 interviewer。

  属后续阶段，本文范围外；
- **不做**会话中途动态改计划（v1，见 §8 风险 4）。

## 11. 实施偏差记录（5.1~5.5 落地后回写）

1. **"计划先于第一题"的实现方式变了（阶段 5.5 节）**
   原设计把流水线拆成 Java 编排三步（分析子图 → ensurePlan → 直连面试官）。实施时确认：
   `LlmRoutingAgent` 的 subAgents 只接受编排图（Agent 实例），Java 步骤插不进路由子图——
   除非让路由层绕开 LlmRoutingAgent（违背 4.2 的语义路由决策，不值）。
   落地改为【临时计划 + 自动升级】：首轮组装上下文时 ensurePlan 立即按用户消息生成
   USER 临时计划（第一题就有出题基准）；JD 画像落库后的下一轮，ensurePlan 探测到
   JD 画像 → 自动升级重生成（source=JD）。覆盖矩阵以最终 JD 计划为基准，
   临时计划期的题目不在最终词表内的按"计划外"如实呈现。
2. **新增"规则前置分诊"（原计划未提及，阶段 5.5 节）**
   `detectMaterials`（路径/扩展名/关键词）命中 → 直接进流水线（省一次路由 LLM 调用，
   组合判断确定性 100%）；`LlmRoutingAgent` 只兜规则漏掉的语义表述（"看看上周写的线程池"）。
   与"复用快路径"同一哲学：能确定答案的便宜事不问 LLM。
3. **路由注册全量组合 + 分析官【资料守门】（原计划未提及，阶段 5.5 节）**
   路由子 Agent 只能是固定图，无法按消息动态选分析官，故 material-interview 注册全量组合
   （三个分析官都在），每个分析官 prompt 末尾拼【资料守门】（ProfileAnalyzerAgent 统一追加）：
   没有自己负责的资料 → 直接结束、禁止调工具、禁止落库。规则误报（关键词命中但资料不在）
   与全量组合下"缺哪类资料"都由守门自筛，把"没资料"变成一条显式且极简的执行路径。
4. **其余按计划落地**：数据契约（interview_plan 表、score_record 零 schema 改动改写入方）、
   三个 LLM 函数（非 Agent）、删 scoreRecord 工具、报告独立端点（GET）、五阶段提交粒度，
   均与计划一致。运行时验收（答砸→当场调难度 / 报告对账）需连真实模型与中间件，待演示环境执行。
