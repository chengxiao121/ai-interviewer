# AI 智能面试官项目 —— 简历级实施计划

> 项目定位：基于 Spring AI Alibaba 1.1 从 0 到 1 构建的 AI 智能面试官（多 Agent 面试陪练系统），
> 具备记忆、知识检索（题库 RAG）、工具调用三大核心能力，并支持多 Agent 协作编排。
> 一句话介绍：**「用自己做的 AI 面试官准备面试」**。

## 技术栈

- Spring Boot 3.5.7
- Spring AI 1.1.2
- Spring AI Alibaba 1.1.2.0
- 阿里百炼 OpenAI 兼容协议（qwen3.7-plus / qwen3.7-text-embedding，DashScope 原生协议不可用）
- Redis Stack（短期记忆 + 题库向量检索）
- PostgreSQL 16（业务数据持久化 + 题库文档元数据）
- Spring Data JPA（业务数据访问层）
- MCP（阶段 2.5 自研 MCP Server，暴露题库/评分能力）
- Docker Compose（本地环境一键启动）

---

## 总体架构

```
用户 ──REST API──> AssistantController (SSE 流式)
                      │
                      ▼
              ┌─ 意图路由 Agent (LlmRoutingAgent) ─┐
              │                                    │
         闲聊 Agent                       多 Agent 工作流（阶段4）
       (纯 LLM 对话)               (代码分析 → 面试官 → 评估闭环)
              │                                    │
              └───────────────┬────────────────────┘
                              ▼
                      Agent 核心能力层
         ┌──────────────┬──────────────┬──────────────────┐
         ▼              ▼              ▼                  ▼
     短期记忆        跨会话薄弱点回顾   工具调用            知识检索
  Redis 滑动窗口   评分结构化聚合     @Tool 自定义        RedisStack 向量库
  (会话隔离)     (阶段4,SQL聚合)   (评分/统计/收藏)   (面试题库+分块+Embedding)
         │              │              │                  │
         └──────────────┴──────────────┴──────────────────┘
                              ▼
                   Redis Stack │ PostgreSQL (业务数据+题库元数据)
                              │
                  MCP Server (自研, @McpTool 暴露题库/评分能力)
```

- 验收：两个容器健康运行

### docker-compose.yml

```yaml
services:
  # Redis Stack：短期记忆 + 向量检索（必须 Stack 版，普通 Redis 没有向量模块）
  redis-stack:
    image: redis/redis-stack:latest
    container_name: redis-stack
    ports:
      - "6379:6379"    # Redis 服务
      - "8001:8001"    # RedisInsight 可视化界面（浏览器打开 localhost:8001 看向量数据）
    volumes:
      - redis-data:/data
    restart: unless-stopped

  # PostgreSQL：业务数据 + 题库文档元数据（阶段 2.2）
  postgres:
    image: postgres:16
    container_name: aiagent-postgres
    environment:
      POSTGRES_USER: admin        # 初始数据库用户名
      POSTGRES_PASSWORD: admin123 # 该用户的密码（仅本地开发用）
      POSTGRES_DB: aiagent        # 初始化时自动创建的默认数据库名
    ports:
      - "5432:5432"
    volumes:
      - pg-data:/var/lib/postgresql/data
    restart: unless-stopped

volumes:
  redis-data:
  pg-data:
```

### AgentConfig 改造要点

- `InMemoryChatMemoryRepository` → **手动创建** `JedisRedisChatMemoryRepository` Bean（memory-redis jar 不带自动装配，连接参数复用 `spring.data.redis.*`）
- 删除手写的 `SimpleVectorStore` Bean（Redis 向量库自动装配 `VectorStore`）
- 保留 `MessageChatMemoryAdvisor` + `QuestionAnswerAdvisor`（Builder 写法不变）
- 删除 `OpenAiApi`、`EmbeddingModel`、`SimpleVectorStore` 导入（不再使用）

```java
@Configuration
public class AgentConfig {

    // 短期记忆存储：Redis 持久化（memory-redis starter 不带自动装配，手动创建 Bean）
    // 连接参数复用 spring.data.redis.* 配置，不用再写死
    @Bean
    public ChatMemoryRepository chatMemoryRepository(RedisProperties redisProperties) {
        return JedisRedisChatMemoryRepository.builder()
                .host(redisProperties.getHost())
                .port(redisProperties.getPort())
                .database(redisProperties.getDatabase())
                .build();
    }

    // 短期记忆：滑动窗口 + Redis 持久化。
    // maxMessages 调大到 60：qwen3.7-plus 上下文窗口 1M token，一场面试全部历史
    // (~3万 token) 远未到上限，直接全量装入，无需摘要压缩（原 3.2 摘要方案已砍，见阶段 3 说明）。
    @Bean
    public ChatMemory chatMemory(ChatMemoryRepository chatMemoryRepository) {
        return MessageWindowChatMemory.builder()
                .chatMemoryRepository(chatMemoryRepository)
                .maxMessages(60)
                .build();
    }

    // 记忆顾问：自动把历史消息注入每次请求（会话由 sessionId 隔离）
    @Bean
    public MessageChatMemoryAdvisor chatMemoryAdvisor(ChatMemory chatMemory) {
        return MessageChatMemoryAdvisor.builder(chatMemory).build();
    }

    // RAG 顾问：VectorStore 由 spring-ai-starter-vector-store-redis 自动装配（Jedis 客户端）
    @Bean
    public QuestionAnswerAdvisor questionAnswerAdvisor(VectorStore vectorStore) {
        return QuestionAnswerAdvisor.builder(vectorStore)
                .searchRequest(SearchRequest.builder()
                        .similarityThreshold(0.7)
                        .topK(3)
                        .build())
                .build();
    }

}
```

> ⚠️ 记忆仓库实现类在 1.1.2.0 已按客户端拆分为 `Jedis/Lettuce/RedissonRedisChatMemoryRepository`（不再有统一的 `RedisChatMemoryRepository`），本项目用 Jedis 版，与向量库客户端保持一致。

- `/api/assistant/chat` 端点正常流式返回
- 同一 sessionId 内多轮对话有记忆
- Redis 里能看到记忆和向量相关的 key

## 阶段 2：单 Agent 完整闭环（3~4天）⭐ 核心阶段

### 2.1 短期记忆

- `JedisRedisChatMemoryRepository` 持久化 + `MessageWindowChatMemory` 滑动窗口（`maxMessages=60`，qwen3.7-plus 1M 窗口下一场面试全量装入，不做摘要压缩）
- 会话隔离：`sessionId` → `ChatMemory.CONVERSATION_ID`
- 新增会话管理 API：查历史、清空会话
- 面试场景落点：会话内多轮追问不重复、不丢上下文（「我刚才答的第三题是什么」）

### 2.2 RAG 完整链路

**题库文档存储：外部目录为主，classpath 兜底**

- 知识库内容 = 面试题库 / 八股 / 岗位 JD 文档（运营方维护，非用户上传）
- 配置项 `app.knowledge.path=file:./data/knowledges/`，默认指向项目根目录下 `data/knowledges/`
- 启动时加载逻辑：
  1. 外部目录不存在 → 自动创建，日志提示"已创建目录，把文档放这里"
  2. 目录存在且有文件 → 使用外部文档（真实题库优先）
  3. 目录为空 → 回退 `classpath:knowledges/*.txt`（示例题库，保证开箱即用）
  4. 日志明确打印当前数据源，避免误判
- 好处：改题库不用重新打包/重启；`ResourcePatternResolver` 原生支持 file:/classpath: 双协议，将来换对象存储只改一个配置

**题库文档元数据入 PostgreSQL**：新建 `KnowledgeDocument` 表（文件名、块数量、入库时间、状态、内容哈希）

- 幂等入库：启动时对比目录与元数据表，哈希/块数未变化的文档跳过，新增/变更才重新入库
- 增量删除：目录中已删的文档 → 按 docId 前缀清理 Redis 中对应块

- `KnowledgeBaseService`：扫描目录 → `TokenTextSplitter` 分块 → `vectorStore.add()` 入库（块级元数据 docId/chunkIndex 随向量写入 Redis）
- 用 `ApplicationRunner` 启动时自动入库 + 手动入库 API
- ⚠️ 维度对齐：RedisVectorStore 1.1.2 建索引时按 `EmbeddingModel.dimensions()` 实时取值（实测 qwen3.7-text-embedding 默认 1024 维，与已建索引 `ai-agent-index` dim=1024 一致，无需手动改索引；启动时打印维度日志留证）
- 验收：对话「考我一道 Java 并发题」能引用题库文档回答；PG 表有入库记录；目录增删文档后重启/调 API 能增量同步

### 2.3 Function Calling 自定义工具 ⭐ 简历重点

> 工具取舍（与初版相比已精简）：砍掉无业务场景的 `currentDateTime`（时间戳由服务端落库时 `now()` 生成）和 `favoriteQuestion`（无用户体系、题目文本已冗余存于评分记录）；`interviewRecord` 推迟到阶段 4（2.3 单 Agent 无面试生命周期概念，待阶段 4 多 Agent 编排落地时连同评估报告一起做）。

| 工具              | 说明                  | 技术亮点                                      |
| --------------- | ------------------- | ----------------------------------------- |
| `calculator`    | 通用算术/平均分计算          | 纯函数工具：数值计算外包，避免 LLM 算术幻觉                  |
| `scoreRecord`   | 保存单题评分              | **PostgreSQL 持久化**，展示 Function Calling 落库 |
| `questionStats` | 答题统计（各考点平均分/题数/薄弱点） | 聚合查询 + 落库                                 |

- 用 `@Tool` + `@ToolParam` 注解，注册到 ChatClient 的 `defaultTools()`
- 新建 `ScoreRecord` 实体 + JPA 仓储（字段：sessionId / topic / question / answer / score / feedback / createdAt）
- ⚠️ 技术风险：当前 `chat()` 走 SSE 流式（`.stream().content()`），Spring AI 1.1.2 流式下工具调用支持有限，先实测确认工具触发链路再定注册方式
- 验收：对话「考我一道 Java 并发题」「我答得怎么样，记下来」「我有哪些薄弱考点」链路全通

### 2.4 可观测性

- `SimpleLoggerAdvisor` 打印请求/响应日志
- 工具调用日志（记录每次 Tool 调用的名称、入参、耗时）

### 2.5 MCP 工具生态（⭐ 2026 热点）

> **方向调整**（实施时论证后修改）：砍掉原计划的「自研 MCP Server 暴露题库/评分能力」——
> 现有三个工具（scoreRecord/questionStats/calculator）强绑定 sessionId 和内部表结构，
> 没有外部进程会通过 MCP 协议远程调用它们，套 JSON-RPC 只有零架构收益，面试时也无法回答"为什么用 MCP"。
>
> 改为**作为 MCP Client 接入外部工具生态**，补齐面试 agent 的真实能力缺口：
> agent 的知识边界原只有静态 RAG 题库，题库外的主题无能为力。

- **MCP Client 接入 Filesystem Server**：`spring-ai-starter-mcp-client` + STDIO 传输，通过 npx 启动官方 `@modelcontextprotocol/server-filesystem`，读取候选人本地项目代码，实现**代码评审式面试**——针对真实实现提问（如"你这里为什么用 SETNX？高可用场景有什么风险？"）
- **ReadOnlyMcpToolFilter**：自定义 `McpToolFilter`，按 MCP 规范的 `annotations.readOnlyHint` 过滤掉 write_file/edit_file/move_file/create_directory 等写操作，保证面试 agent 只读不改
- **降级兼容**：`ObjectProvider<ToolCallbackProvider>` 注入，未配置 MCP 或 npx 拉包失败时只用内置 @Tool，核心面试功能不受影响
- ~~Fetch MCP~~：原计划接入 `@modelcontextprotocol/server-fetch` 读取 URL 内容出题，但该 npm 包已下架（404），待后续找替代方案补齐
- 验收：对话「看看 D:\...\InterviewTools.java 这个文件，针对我的实现问我几个问题」→ agent 调 read_file 读取真实代码 → 针对实现细节提问（已验证通过）

### 阶段验收标准

一个求职者可以通过对话完成「被出题 → 答题 → 追问 → 评分落库 → 查薄弱点」的完整闭环，出题能引用题库知识。

### 3.2 流式输出优化

- 保持 SSE 流式（打字机效果），出题/追问/评估各阶段输出中间状态提示（如「正在评估你的回答…」）

### 验收标准

- ReactAgent 显式推理链路可观测（思考/行动/观察节点日志可见）
- SSE 流式稳定输出，各阶段有中间状态提示

> ~~3.2 自研摘要式长期记忆~~（已砍掉，理由见下）
>
> **为什么砍掉会话内跨窗口摘要**：
> 查证 qwen3.7-plus 上下文窗口为 **1M token（约 70 万汉字）**，一场 30~60 轮面试
> 的全部历史才 ~3 万 token，离上限差三十多倍，**面试场景根本不会溢出上下文窗口**。
> 原"摘要压缩解决窗口限制"的立论不成立；被追问"你真的溢出过吗"时无法自圆。
> 故改为**直接调大 `MessageWindowChatMemory` 窗口**（20 → 60，一场面试全量装入），
> 记忆架构亮点全部押到阶段 4.3 的**跨会话薄弱点回顾**（引入候选人标识 + SQL 聚合，
> 那才是本项目真正有设计含量、经得起追问的记忆难题）。
> 调窗口改动见阶段 1 `AgentConfig` 的 `chatMemory` Bean。

## 阶段 4：多 Agent 协作编排（3天）⭐ 进阶亮点

> 学习路径：不搞"为了多 Agent 而多 Agent"，三步逐级加深，每步都有独立验收 + 简历话术增量：
> ① 双 Agent 分工与数据契约（最简单编排，一定能跑通）→ ② 意图路由 + 并行（动态决策）
> → ③ 反馈闭环（评估反哺，跨会话记忆）。**三步走完 = 有状态、有决策、有反馈的完整多 Agent 系统。**
>
> 场景落点：**不换场景**，把已有的「代码评审式面试」升级成多 Agent 协作——
> MCP Filesystem 读代码已就位，分析能力现成，改动面最小、学习收益最大。

### 4.1 双 Agent 流水线：代码分析 Agent → 面试官 Agent（1天）

**做什么**

- 新建 `CodeAnalyzerAgent`（ReactAgent）：MCP filesystem 读候选人代码 → 产出**结构化事实清单**（JSON：技术栈 / 设计模式 / 实现细节 / 潜在风险点 / 可追问点）→ 落库新表 `code_profile`（sessionId / filePath / factsJson / createdAt）
- 改造 `InterviewAssistant` 为「面试官 Agent」：不再持有代码评审 prompt，改为从 `code_profile` 取事实清单，基于清单出题追问
- `SequentialAgent` 编排：分析 Agent → 面试官 Agent（「开始代码评审面试」 = 一条双 Agent 流水线）

**学到什么（多 Agent 核心概念）**

- Agent 分工：**分析型**（读、理解、产出结构化数据）vs **对话型**（基于结构化物料做决策）
- Agent 间**数据契约**：结构化 JSON 传递，不是文本拼接——这是多 Agent 与"多 prompt 单 agent"的本质区别

**技术要点**

- LLM 结构化输出可靠性：提示词要求 JSON + Jackson 容错解析，解析失败降级纯文本，不阻塞面试
- 事实清单**落库而非内存传递**：面试官按需取，重开会话（同 sessionId）不重复分析
- 记忆归属：沿用阶段 3 现有机制——短期记忆由会话层统一读写，子 Agent 无状态

**验收**：对话「看看 D:\...\InterviewTools.java，针对我的实现考我」→ 分析 Agent 读代码 → 事实清单落库可见 → 面试官基于清单出题追问。链路走双 Agent，日志可见两个 agent 节点。

### 4.2 意图路由 + 并行分析（1天）

**做什么**

- `LlmRoutingAgent` 入口，三类意图：
  - 「代码评审面试」→ 4.1 双 Agent 流水线
  - 「直接出题面试」→ 仅面试官 Agent
  - 「闲聊」→ 闲聊 Agent；`fallbackAgent` 指向面试官 Agent（主场景兜底）
- `ParallelAgent`：JD 分析 / 简历分析 / 代码分析 三个分析 Agent **并行**跑，`ConcatenationMergeStrategy` 合并事实清单，统一交给面试官 Agent

**学到什么（多 Agent 核心概念）**

- 意图路由：LlmRoutingAgent + fallback 策略
- 并行编排与结果合并策略

**技术要点**

- 新增的 JD/简历分析 Agent 与 4.1 的 CodeAnalyzerAgent 同构（同一套「读文件 → 结构化清单」模式）；JD/简历可以是本地文件（MCP 读）或对话中粘贴的文本
- 全部用现有 framework：`LlmRoutingAgent.builder().subAgents(...)`、`ParallelAgent.builder().mergeStrategy(...)`
- 不单独做知识 Agent：知识问答是面试官 Agent 的既有 RAG 能力，避免第三路误路由（面试中问「什么是 AQS」切走上下文）

**验收**：同一入口说不同意图（看代码考我 / 直接考我 / 闲聊），路由到正确 Agent 组合；「看 JD+简历+我的代码一起考我」→ 三个分析并行 → 合并清单 → 面试官一并出题。

### 4.3 反馈闭环 + 跨会话薄弱点回顾（1天）⭐ 记忆亮点落点

> 原 4.2b「跨会话薄弱点回顾」移到这里——这是整个项目最经得起追问的记忆难题
> （有别于已被论证为伪命题的会话内摘要），同时也是多 Agent "反馈闭环"的载体。

**做什么**

- **候选人对齐**：引入 `candidateId`（同一求职者的多次会话挂同一 id）。
  先做轻量方案：前端传入 `candidateId`（或用固定值占位），`ScoreRecord` 增 `candidateId` 字段，
  `scoreRecord` 工具落库时写入（sessionId 仍保留用于会话内隔离）。
- **薄弱点聚合工具**：新建 `getWeaknessProfile(candidateId)`——跨该候选人所有 `ScoreRecord`
  按考点聚合（答题数/平均分/最低分），标注平均分 <6 的薄弱考点。
  复用现有 `ScoreRecordRepository.aggregateByTopic` 的思路，改为按 `candidateId` 聚合。
- **闭环注入**：新会话开始 / 用户说「继续上次的面试」时，面试官 Agent 调
  `getWeaknessProfile` 取回历史薄弱点，注入 system prompt，
  重点考察上次没答好的点（如「上次你 Redis 持久化答得不好，这次重点考察」）；
  代码评审场景下，分析结果与薄弱点一并回写 `code_profile`，作为下次分析的输入。
- **走 SQL 聚合路线，不走摘要/向量化**：薄弱点已是 `score_record` 表里的结构化数据，
  SQL 聚合精度高、零幻觉、零额外 LLM/embedding 成本；摘要+向量会丢精度、引入幻觉，是过度设计。
- 简历数据源合流（原 4.3）：面试官 Agent 同时消费 ①简历/JD 画像 ②跨会话薄弱点
  ③题库 RAG 三路物料，`searchResume` / `getResume` 工具按需取。

**学到什么（多 Agent 核心概念）**

- **反馈闭环**：下游 Agent 的产出（评估）结构化反哺上游 Agent（出题/分析），横跨多个 Agent 与多次会话——这就是多 Agent 系统的状态管理
- 结构化反哺 vs 摘要/向量化的取舍论证（精度、幻觉、成本三条）

**验收**：会话 A 代码评审答完若干题拿到评分 → 新会话 B（同 candidateId）→ 面试官开局主动提及 A 的薄弱考点并重点考察。

### 阶段 4 验收标准

同一入口问不同类型问题（看代码考我 / 直接考我 / 闲聊 / JD+简历+代码一起）自动路由到正确 Agent 组合；代码评审走「分析 → 面试」双 Agent 链路且事实清单落库可见；并行分析合并正确；**同 candidateId 新会话能召回旧会话薄弱考点并重点考察**。

## 关键风险提示

1. **Redis 必须用 Stack 版**（普通 Redis 无向量检索模块）
2. `initialize-schema: true` 首次启动自动建向量索引，之后可关
3. API Key 开发期硬编码，公开仓库前移到环境变量并去百炼控制台重置（旧 key 已在 git 历史里）
4. **向量维度已实测对齐**：qwen3.7-text-embedding 默认 1024 维，与已建索引一致；若换模型/改 dimensions 参数，需先检查索引维度
5. **Windows 中文系统 JVM 默认 GBK**，会导致 Redis 记忆中文乱码（存成 `?`）：项目根目录 `.mvn/jvm.config` 已加 `-Dfile.encoding=UTF-8`；IDEA 直接运行时 Run Configuration 的 VM options 也要加
6. **本机若装有原生 Redis 会抢占 6379**：普通 Redis 无向量模块，应用连上后会报 `unknown command 'FT._LIST'`，需停掉原生 Redis（`net stop Redis`）
7. **Spring AI 1.1.2 Redis 向量库自动装配强依赖 Jedis 客户端**：必须 `spring.data.redis.client-type=jedis` + `commons-pool2`，否则 VectorStore Bean 创建失败
8. 每个阶段结束都 git commit，方便简历上展示 commit 历史
9. **PostgreSQL 连接信息以根目录 docker-compose.yml 为准**（admin/admin123，库 aiagent），与本文档早期版本不同
10. 外部知识目录 `data/knowledges/` 默认 gitignore（示例题库放 `resources/knowledges` 兜底），避免内部资料被提交进公开仓库
11. **SSE 流式走 WebClient（Netty）**：DNS 解析在部分网络环境会超时导致流式 500，需把 `WebClient.Builder` 也换 JDK 客户端（已通过 `HttpClientConfig` 处理，RestClient + WebClient 都改）
12. **模型可能对同一道题重复调用 scoreRecord**：会导致重复落库污染统计，工具内已按 `sessionId+question` 幂等去重
13. **Function Calling 需在 SSE 流式下实测**：Spring AI 流式默认会执行工具调用并回填结果，工具调用中间 token 会混进流，前端按 SSE 拼接即可
14. **FlowAgent 流式需实测**：SequentialAgent / LlmRoutingAgent / ParallelAgent 的 `streamMessages` 继承自 Agent 基类，理论支持 SSE；但多节点流水线的中间产物流式形态需实测确认（阶段 4）
15. **LLM 结构化输出不可全信**：事实清单 JSON 可能解析失败（多余引号、非 JSON 文本、字段缺失），必须 Jackson 容错解析 + 降级纯文本兜底，不能让一个坏 JSON 中断整个面试流程（阶段 4.1）
16. **路由误判兜底**：LlmRoutingAgent 的 `fallbackAgent` 必须指向面试官 Agent（主场景），意图分类失败时仍能完成核心面试功能（阶段 4.2）
